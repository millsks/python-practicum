Growth rates

Big-O describes how cost grows with input size n, ignoring constant factors. Below, n is the container size, k is the size of the argument or result, V/E are vertices and edges. "Amortized O(1)" means an occasional expensive step averages out to constant per operation. "Average" for hash tables assumes a decent hash function; the worst case (all keys colliding) is O(n).

Rule of thumb for pure Python: roughly 107 simple operations per second. With n = 105, O(n log n) finishes instantly and O(n²) takes minutes.

NumPy and pandas vectorization

NumPy and pandas operations have the same Big-O as the equivalent Python loop, often O(n), but the loop runs in compiled code over contiguous memory, so the constant is 10–100× smaller. The rule: push loops into the library.

Which structure should I use?

flowchart TD
  Q{"What do you mostly do?"} --> A["Look up by key"]
  Q --> B["Keep things in order"]
  Q --> C["Take the smallest or largest next"]
  Q --> D["Add and remove at the ends"]
  Q --> E["Test membership or de-duplicate"]
  Q --> F["Heavy numeric math"]
  A --> A1{"Need the keys sorted?"}
  A1 -- no --> A2["dict  O(1)"]
  A1 -- yes --> A3["sorted list + bisect, or a balanced tree"]
  B --> B1{"Mostly append and index?"}
  B1 -- yes --> B2["list"]
  B1 -- "insert in the middle often" --> B3["bisect.insort for small n, else a balanced tree"]
  C --> C1["heapq  O(log n)"]
  D --> D1{"Only one end?"}
  D1 -- "yes, LIFO" --> D2["list as a stack"]
  D1 -- "both ends or FIFO" --> D3["collections.deque"]
  E --> E1{"Need counts?"}
  E1 -- no --> E2["set  O(1)"]
  E1 -- yes --> E3["Counter"]
  F --> F1["NumPy array or pandas / Polars"]
