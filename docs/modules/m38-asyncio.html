Async Programming with asyncio

One thread, thousands of concurrent network calls, and no locks around your data structures: that's the promise of asyncio. It delivers, but only if you understand the event loop well enough to never block it, to structure tasks so none leak, and to handle timeouts and cancellation correctly. This module builds that understanding from the loop up.

The event loop mental model

In M37 you saw that threads overlap I/O waits, but they bring preemptive switching and therefore races at any instruction. asyncio takes a different approach called cooperative multitasking. All your tasks run in one thread. A task runs until it reaches an await on something that isn't ready yet (a network reply, a timer); at that point it voluntarily suspends and hands control back to the event loop. The loop then runs another task that is ready. When the reply arrives, the loop marks the waiting task ready again and resumes it exactly where it left off.

Conceptually, the loop is just this:

while tasks_exist:
    run every callback in the READY queue        # each runs until its next await
    wait for I/O or the next timer (selectors / epoll / kqueue / IOCP)
    move tasks whose I/O or timer completed to the READY queue

Three consequences follow from "one thread, switch only at await":

  • Races are rarer and visible. Code between two awaits runs without interruption, so self.count += 1 needs no lock. But any check → await → act sequence can still interleave with other tasks (you'll see this in Project 5).
  • Blocking is catastrophic. A task that calls time.sleep(1) or a blocking HTTP library freezes every task for that second, because the loop can't run anything else until it returns.
  • No parallelism. asyncio is for I/O-bound concurrency. CPU-heavy work stalls the loop just like blocking I/O; offload it (see Mixing in blocking code).

A normal script starts the loop with asyncio.run(main()), which creates a loop, runs main() to completion, cancels leftovers, and closes the loop. In this course's browser cells an event loop is already running (Pyodide drives asyncio from the browser's own event loop), so asyncio.run() would fail with "cannot be called from a running event loop". Instead, the cells use top-level await main(), the same thing python -m asyncio's REPL allows. When you copy code into a .py file, replace await main() with asyncio.run(main()).

Coroutines, await, and Tasks

Precise vocabulary prevents most asyncio confusion:

TermWhat it is
Coroutine functionA function defined with async def. Calling it does not run its body.
Coroutine objectWhat calling a coroutine function returns: a paused computation. It runs only when awaited or wrapped in a Task.
AwaitableAnything usable after await: coroutines, Tasks, Futures, objects with __await__.
TaskA coroutine scheduled to run on the loop independently. Created by asyncio.create_task or TaskGroup.create_task. It's a subclass of Future.
FutureA low-level placeholder for a result that will be set later (by a callback, a thread, or the loop).

The crucial difference: await coro() runs the coroutine now, inside the current task, and waits for it. Concurrency only happens when you create Tasks, because each Task is a separate entry the loop can switch between. Under the hood, a coroutine is a generator-like object: await works much like yield from, passing suspension requests up to the Task that drives it.

Keep a reference to every task you create. The event loop holds only weak references to tasks. A "fire and forget" asyncio.create_task(job()) whose result you don't store can be garbage-collected mid-flight, and an exception inside it is reported only as a "Task exception was never retrieved" log line, if at all. The fix is structural: create tasks in a TaskGroup, or store them in a set and discard them in a done-callback.

gather vs TaskGroup: structured concurrency

asyncio.gather(*aws) runs awaitables concurrently and returns their results in argument order. Its error handling is the problem: by default, the first exception propagates to the awaiting code, but the other tasks keep running, unsupervised, in the background. With return_exceptions=True, exceptions are returned as values in the result list, which is handy for "try everything, report failures" but easy to forget to check.

asyncio.TaskGroup (3.11+) implements structured concurrency: tasks are created inside an async with block and cannot outlive it. The block waits for all of them. If any task fails, the group cancels all the others, waits for them to finish cancelling, and raises an ExceptionGroup containing every failure. Lifetimes are visible in the code's indentation, like variables in a scope.

The except* syntax (3.11+) matches exceptions inside an ExceptionGroup: each except* clause handles the matching subgroup, and anything unmatched is re-raised. Several clauses can run for one group.

Default to TaskGroup. Use gather(..., return_exceptions=True) when you deliberately want "run all, collect all outcomes" and you check every result. Note that one task failing in a TaskGroup cancels its siblings; if you want independent jobs to keep going, catch the exception inside each job and return an error value instead of raising.

Timeouts

Every network operation needs a timeout; a peer that never answers otherwise hangs your task forever. async with asyncio.timeout(seconds): (3.11+) cancels the enclosed code if it runs too long and converts that cancellation into TimeoutError at the async with boundary. Because it scopes a block, one deadline can cover several awaits (connect, send, read). Related tools:

  • asyncio.timeout_at(loop.time() + n): an absolute deadline, ideal for propagating one budget through nested calls.
  • cm.reschedule(new_deadline) on the context manager to extend or shorten it; timeout(None) means "no deadline yet".
  • asyncio.wait_for(aw, timeout): the older single-awaitable form, now implemented with timeout.

Cancellation semantics

Cancellation is asyncio's mechanism for stopping work: timeouts, TaskGroup failures, and shutdown all use it. task.cancel() doesn't kill anything immediately. It schedules a CancelledError to be raised inside the task at its current (or next) await. The task can then run cleanup in finally blocks and async with exits, and must let the exception propagate.

  • CancelledError inherits from BaseException, not Exception, so a generic except Exception: doesn't swallow it. Never catch it without re-raising (unless you are the code that requested the cancellation, and even then prefer the structured tools).
  • Cleanup code may await (closing a connection), but keep it short: a second cancel can interrupt it.
  • asyncio.shield(aw) protects an inner awaitable from cancellation of the outer task: the outer await is cancelled, but the inner operation keeps running. Use it rarely (for example, finishing a commit).
  • Internally, tasks count cancellation requests (task.cancelling(), task.uncancel()); this is how timeout() and TaskGroup distinguish their own cancellations from yours.

A try: ... except BaseException: pass or a bare except: in a coroutine silently eats cancellation; the task keeps running after a timeout "fired", and TaskGroups hang on exit. If you must catch broadly, re-raise asyncio.CancelledError first.

Producer/consumer with asyncio.Queue

asyncio.Queue mirrors queue.Queue but its put/get are coroutines that suspend instead of blocking a thread. It's not thread-safe; it's for tasks on one loop. The standard worker-pool shape:

  1. Create the queue (optionally with maxsize for back-pressure) and N worker tasks.
  2. Each worker loops: item = await queue.get(), process, and queue.task_done() in a finally.
  3. The producer puts items; then await queue.join() waits until every item is done.
  4. Stop workers: cancel them, put one sentinel per worker, or (3.13+) call queue.shutdown(), which makes pending and future get() calls raise asyncio.QueueShutDown once the queue is empty.

queue.shutdown(immediate=True) also discards items still in the queue, which suits "stop now" shutdowns. The sentinel pattern still works everywhere and is what Project 5 uses, because there the workers themselves are producers and only queue.join() knows when the crawl is truly done.

Limiting concurrency and rate

Creating 10,000 tasks is cheap; opening 10,000 simultaneous connections to one server is rude and usually fails. Two different limits are often needed:

  • Concurrency limit (how many at once): asyncio.Semaphore(n). Each task does async with sem: around the request; at most n are inside.
  • Rate limit (how many per second): a token bucket or a minimum interval between starts. A semaphore alone doesn't bound rate: fast responses let tasks cycle through it quickly.

Why does a single-threaded program need asyncio.Lock? Inside acquire there's no await between reading and updating next_time, so it's actually safe here. But the moment someone adds an await in that section (say, logging to an async sink), it becomes a race. The lock documents and enforces the critical section.

Async iterators, generators, and context managers

Some protocols need to await in the middle: fetching the next page of results, or closing a connection. Python has async versions of the iteration and context-manager protocols:

An async generator abandoned halfway (for example by a break in an async for) can't run its finally synchronously; the loop finalizes it later. When the generator holds a resource, wrap it with contextlib.aclosing(gen) so cleanup happens at a known point.

Mixing in blocking code

Not every library is async. A synchronous database driver, requests, urllib, or a CPU-heavy function will block the loop. The bridges:

  • await asyncio.to_thread(func, *args) (3.9+): run a blocking function in the loop's default thread pool; perfect for blocking I/O (the GIL is released while it waits). This is how Project 5's real fetcher uses urllib.
  • await loop.run_in_executor(executor, func, *args): the same with an executor of your choice; use a ProcessPoolExecutor (or InterpreterPoolExecutor) for CPU-bound work.
  • asyncio.run_coroutine_threadsafe(coro, loop): the reverse direction, submitting a coroutine to a loop running in another thread (returns a concurrent.futures.Future).

Run with asyncio.run(main(), debug=True) or PYTHONASYNCIODEBUG=1 during development. Debug mode warns about coroutines that were never awaited, logs any callback that blocks the loop for more than loop.slow_callback_duration (100 ms), and reports non-threadsafe calls.

Inspecting running async programs

Python 3.14 can show you what a live asyncio program is doing, from the outside, without modifying it. Using the safe external debugger interface (PEP 768), the asyncio CLI attaches to a running process by PID:

pixi run python crawler.py &              # some long-running asyncio program
pixi run python -m asyncio ps 12345         # flat table: every task, its name, coroutine stack, awaiter
pixi run python -m asyncio pstree 12345     # tree: which task is awaiting which

This is invaluable for "why is my service stuck?" questions: a task waiting forever on a lock or a queue shows up immediately, and pstree also detects await cycles. (Attaching to another process may require permissions, for example running as the same user; on macOS it may need elevated privileges.)

Inside a program, the same information is available as an API. asyncio.capture_call_graph(task) returns a FutureCallGraph (the task, its coroutine call stack, and who awaits it); asyncio.print_call_graph(task) and format_call_graph render it. Omit the argument to describe the current task.

Preview: TaskGroup.cancel() in 3.15

Python 3.15 adds TaskGroup.cancel(), a direct way to stop every task in a group without treating it as an error. In 3.14, "stop the group when the first result arrives" requires raising a private exception in one task and catching it with except* outside the group, or cancelling each task by hand. With 3.15, the group exits normally after cancelling its children.

Practice

Write async def fetch_all(urls, fetch) that calls the async function fetch(url) for every URL concurrently using an asyncio.TaskGroup, and returns a dict mapping each URL to its result. Duplicated URLs must be fetched only once.

Hint

Create one task per unique URL inside the async with block, keep them in a dict, and read task.result() after the block. dict.fromkeys(urls) de-duplicates while keeping order.

Show solution 
import asyncio

async def fetch_all(urls, fetch):
    async with asyncio.TaskGroup() as tg:
        tasks = {url: tg.create_task(fetch(url)) for url in dict.fromkeys(urls)}
    return {url: task.result() for url, task in tasks.items()}

Write async def bounded_map(func, items, limit) that awaits func(item) for every item with at most limit calls in flight at once, and returns results in input order. Raise ValueError if limit < 1.

Hint

Wrap each call in a small coroutine that does async with sem: return await func(item), then gather them (gather preserves order) or use a TaskGroup and read results afterwards.

Show solution 
import asyncio

async def bounded_map(func, items, limit):
    if limit < 1:
        raise ValueError("limit must be >= 1")
    sem = asyncio.Semaphore(limit)

    async def one(item):
        async with sem:
            return await func(item)

    async with asyncio.TaskGroup() as tg:
        tasks = [tg.create_task(one(item)) for item in items]
    return [t.result() for t in tasks]

Write async def with_fallback(aw, seconds, default) that returns the result of awaiting aw, or default if it takes longer than seconds. Use asyncio.timeout. Other exceptions must propagate. Then write async def first_ok(coros, seconds) that tries each awaitable in order with that timeout and returns the first non-timeout result, or raises TimeoutError if all time out.

Hint

try: async with asyncio.timeout(seconds): return await aw then except TimeoutError: return default. For first_ok, use a unique sentinel object as the default so a legitimate None result isn't mistaken for a timeout.

Show solution 
import asyncio

async def with_fallback(aw, seconds, default):
    try:
        async with asyncio.timeout(seconds):
            return await aw
    except TimeoutError:
        return default

_TIMED_OUT = object()

async def first_ok(coros, seconds):
    for aw in coros:
        result = await with_fallback(aw, seconds, _TIMED_OUT)
        if result is not _TIMED_OUT:
            return result
    raise TimeoutError("every attempt timed out")

Write an async generator countdown(n, log) that yields n, n-1, ..., 1, awaiting asyncio.sleep(0) before each value, and appends "closed" to the list log when it finishes or is closed early. Then write async def take(agen, k) that returns a list of the first k items and closes the generator deterministically (use contextlib.aclosing).

Hint

Put the loop in try and the log.append("closed") in finally. In take: async with aclosing(agen) as g: async for x in g: ..., breaking when you have k.

Show solution 
import asyncio
from contextlib import aclosing

async def countdown(n, log):
    try:
        for i in range(n, 0, -1):
            await asyncio.sleep(0)
            yield i
    finally:
        log.append("closed")

async def take(agen, k):
    out = []
    async with aclosing(agen) as g:
        async for item in g:
            out.append(item)
            if len(out) == k:
                break
    return out

Write async def process_all(items, handler, workers) that pushes every item into an asyncio.Queue, starts workers worker tasks that each await handler(item), and returns the list of results in the same order as items. Use queue.join() to know when all items are processed, and make sure no worker task is still running when the function returns. If a handler raises, the exception must propagate (an ExceptionGroup is fine).

Hint

Queue (index, item) pairs and store results in a list pre-filled with None. Run workers in a TaskGroup; after await queue.join(), put one None sentinel per worker. If a worker crashes, the TaskGroup cancels the body (including the join()), so the error still propagates.

Show solution 
import asyncio

async def process_all(items, handler, workers):
    queue = asyncio.Queue()
    results = [None] * len(items)
    for pair in enumerate(items):
        queue.put_nowait(pair)

    async def worker():
        while True:
            job = await queue.get()
            try:
                if job is None:
                    return
                index, item = job
                results[index] = await handler(item)
            finally:
                queue.task_done()

    async with asyncio.TaskGroup() as tg:
        for _ in range(workers):
            tg.create_task(worker())
        await queue.join()
        for _ in range(workers):
            queue.put_nowait(None)
    return results

Mini-project: an async rate-limited fetcher simulator

Mini-projectfetchsim: a polite, resilient async client

Real APIs throttle you (HTTP 429), fail intermittently (503), and occasionally hang. Build a simulator of such an API and a client that fetches 200 resources from it as fast as the rules allow, without ever exceeding the limits. Everything runs locally with asyncio.sleep standing in for the network, so it's fast and deterministic with a seeded RNG.

pixi init fetchsim
cd fetchsim
pixi add python=3.14 pytest
pixi run python fetchsim.py --requests 200 --concurrency 10 --rate 50
pixi run python -m pytest -q

Specification

  • FakeAPI(seed, latency=(0.01, 0.05), error_rate=0.05, hang_rate=0.01, max_rate=50) with async def get(path): sleeps a random latency, sometimes raises ServerError(503), sometimes hangs for 10 s, and returns 429 if called more than max_rate times in any sliding 1-second window.
  • Client with a Semaphore (concurrency), a token-bucket RateLimiter (rate), per-request asyncio.timeout, and retries with exponential backoff and jitter on 503, 429, and timeouts.
  • fetch_many(paths) runs inside a TaskGroup, returns results in input order, and reports stats: successes, retries, timeouts, 429s, p50/p95 latency, and total time.
  • Ctrl+C (or an overall asyncio.timeout) cancels cleanly and prints partial stats.
  • While it runs, inspect it from another terminal with pixi run python -m asyncio pstree <PID>.

Acceptance criteria

  • All 200 requests eventually succeed with the default settings
  • The client never receives a 429 when its rate is set at or below the API's limit
  • Peak concurrency never exceeds the semaphore size (asserted in a test)
  • Hung requests are cut off by the timeout and retried
  • A test cancels fetch_many midway and checks that no tasks remain
  • Tests use an injected sleep/clock or tiny latencies and finish in under two seconds

Quiz

Recap

  • asyncio runs many tasks on one thread, switching only at await; never block the loop.
  • Coroutine functions create coroutine objects; Tasks schedule them concurrently. Keep references, or better, use a TaskGroup.
  • TaskGroup gives structured concurrency and ExceptionGroups; handle them with except*.
  • Use asyncio.timeout for deadlines; cancellation is an exception raised at an await, so clean up in finally and re-raise.
  • asyncio.Queue (with task_done/join, sentinels, or 3.13's shutdown()) builds worker pools; Semaphore bounds concurrency; rate needs its own limiter.
  • async for, async generators, and async with handle protocols that need to await; close generators with aclosing.
  • to_thread and executors bridge blocking code; 3.14 adds python -m asyncio ps/pstree and capture_call_graph.
