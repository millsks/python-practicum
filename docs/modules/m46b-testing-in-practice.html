Testing in Practice

M17 taught you how pytest works. This module teaches you to test real code: code that reads the clock and the environment, logs instead of returning, talks to databases, runs coroutines, and was never designed with tests in mind.

⏱ ~4 hoursPrerequisites: M17 Testing, M38 asyncio, M44 Databases, M46 Design
  • Choose between a real resource, dependency injection, monkeypatch, and patch for each dependency
  • Use every monkeypatch method, and patch where a name is looked up rather than where it is defined
  • Assert on printed output, file descriptors, standard library logs, and structlog events
  • Build factory, autouse, and parametrized fixtures, and control their scope and cleanup
  • Make time, randomness, and coroutines deterministic under test
  • Write integration tests that leave no state behind, and block accidental network calls
  • Diagnose flaky suites, and judge a suite by the bugs it catches rather than by its coverage

Choosing a seam

A seam (M46) is a place where a test can substitute behavior without editing the code. Most testing trouble comes from picking the wrong kind. Work down this list and stop at the first option that fits.

OptionUse it whenExample
The real thingIt is fast and localtmp_path rather than a fake open; in-memory SQLite rather than fake SQL
Inject a fakeYou own the code and can add a parametercheckout(cart, gateway=FakeGateway())
monkeypatchThe value is global state you can't or shouldn't change: environment variables, module constants, the current directorymonkeypatch.setenv("REGION", "eu")
patch / MockYou need to verify an interaction that is the actual behavior, such as "the alert was sent once"mailer.send.assert_called_once_with(...)

monkeypatch and patch overlap. Both replace a name and restore it afterward. The practical difference is that monkeypatch is a pytest fixture that swaps in whatever value you give it, while patch creates a Mock that records its calls. If you don't need the record, a small function passed to monkeypatch.setattr is usually easier to read.

A function calls os.environ["API_URL"], requests.get, and datetime.now(). Which of the three would you remove first if you were allowed to refactor it, and which would you still patch?

Remember: real if it is fast, injected if you own it, patched if it is global, mocked only when the interaction itself is the behavior.

monkeypatch in full

The fixture records the original state of everything it touches and undoes all of it when the test ends, whether the test passed or failed. That automatic cleanup is the reason to use it instead of assigning to os.environ or a module attribute yourself: a forgotten restore leaks into every later test.

MethodWhat it replaces
setattr(obj, "name", value)An attribute on a module, class, or instance
setattr("pkg.mod.name", value)The same, addressed by a dotted string, so you needn't import the module
delattr(obj, "name", raising=True)Removes an attribute
setenv("NAME", "value", prepend=None)An environment variable. Values must be strings; prepend=":" adds to the front, as for PATH
delenv("NAME", raising=True)Removes an environment variable
setitem(mapping, key, value) / delitem(mapping, key)One dictionary entry, such as a config setting or sys.modules
chdir(path)The current working directory
syspath_prepend(path)Adds a directory to the front of sys.path
with monkeypatch.context() as m:Limits patches to one block rather than the whole test

Two details catch people. setattr raises AttributeError if the attribute doesn't exist, which protects you from patching a typo; pass raising=False only when you mean to create it. And delenv raises KeyError if the variable isn't set, so a test of default behavior should use delenv("NAME", raising=False). That is also how you keep a test from depending on the machine it runs on.

monkeypatch is function-scoped, so a scope="session" fixture can't request it. If a wide-scoped fixture needs a patch, create one with pytest.MonkeyPatch() and call its undo() after the yield.

Remember: all changes are undone automatically. Use delenv(..., raising=False) so that default-value tests don't depend on the machine.

Patch where the name is looked up

This is the most common patching bug, and it fails silently. Suppose you have two modules:

def tax_rate(region):
    ...  # calls a remote service
from prices import tax_rate

def gross(net, region):
    return round(net * (1 + tax_rate(region)))

from prices import tax_rate creates a second name, report.tax_rate, bound to the same function when report is imported. Patching prices.tax_rate afterward rebinds the first name only. report still holds the original, and your test makes the real network call. The fix is to patch the name the code actually uses: report.tax_rate.

If the module used import prices and called prices.tax_rate(region), the lookup would happen in prices at call time, and patching prices.tax_rate would be correct. Read the import statement in the module under test before you choose a target. This cell demonstrates both results:

Remember: with from a import b, patch your_module.b. With import a, patch a.b.

Capturing output and logs

Output is behavior too. pytest offers a fixture for each place it can go.

Fixture or toolCapturesTypical check
capsyssys.stdout and sys.stderrout, err = capsys.readouterr()
capfdThe file descriptors, including output from C extensions and subprocessesSame API as capsys
caplogRecords sent through standard library loggingcaplog.records, caplog.text, caplog.at_level(...)
structlog.testing.capture_logsstructlog events, as dictionarieswith capture_logs() as events:

readouterr() drains the buffer, so each call returns only what was written since the previous call. To fake a user typing, replace sys.stdin with monkeypatch. caplog only sees records at or above the active level, and the root logger's default is WARNING. Use caplog.at_level(logging.INFO) to capture lower levels.

Testing structlog

This course's professional code logs with structlog (M42). With its default configuration, structlog doesn't go through standard library logging, so caplog sees nothing. Use capture_logs, which hands you each event as a dictionary. That is easier to assert on than a formatted string, because a change to the log format can't break the test.

Remember: capsys for prints, capfd for anything below Python, caplog for logging, and capture_logs for structlog.

Fixture patterns for real suites

Factories

A fixture normally gives each test one fixed object. When tests need several objects, or small variations, return a function instead. This is the factory fixture. It lets each test state only the fields it cares about, which keeps irrelevant data out of the test.

Autouse

@pytest.fixture(autouse=True) applies a fixture to every test in its scope without being requested. Reserve it for true safety rules, such as resetting global state or blocking the network. Anything else should be requested by name, because hidden setup makes a test harder to read.

Parametrized fixtures

@pytest.fixture(params=[...]) runs every dependent test once per value, available as request.param. This is how you run the same contract tests against each adapter, as in Project 6.

Cleanup and scope

Code after yield runs even if the test fails, but not if the fixture itself raised before reaching the yield. request.addfinalizer(fn) registers cleanup one resource at a time, so you can build several resources safely. Fixtures tear down in reverse order of setup. A fixture may only request fixtures of the same or a wider scope, and tmp_path_factory is the session-scoped counterpart of tmp_path.

That last test relies on running after the previous one, purely to show you the teardown order. Real tests must never depend on order; see suite health.

Where fixtures live

pytest looks for a fixture in the test file, then in each conftest.py walking up the directory tree, then in plugins and built-ins. The closest definition wins, so tests/integration/conftest.py can provide a real db while tests/unit/conftest.py provides a fake with the same name. To see where each fixture a test uses comes from, run pixi run pytest --fixtures-per-test tests/unit/test_cart.py.

Remember: factories for variation, autouse only for safety, params for contract tests, and the closest conftest.py wins.

Parametrize beyond the basics

Readable test ids turn a failure report into documentation. test_fee[at-threshold] tells you what broke; test_fee[5000-0] makes you go and look. pytest.param attaches an id and marks to a single case, and indirect=True sends the values through a fixture rather than straight to the test.

In a real project, an xfail must link to an open issue that explains it. Otherwise it hides a bug forever. Add strict=True so that the suite fails if the test starts passing and the mark is out of date.

Remember: name your cases. Keep logic out of the parameter table, and split a table in two when its rows need different assertions.

Taming time and randomness

A test that reads the real clock passes today and fails on a weekend, at midnight, or on February 29. You have three ways to control time, listed from most to least preferred.

  1. Pass time in. is_overdue(due, today) is a pure function and needs no tricks at all.
  2. Inject a clock. Library(clock=FixedClock(...)), as in Project 2.
  3. Freeze the clock from outside. Use this for code you can't change yet. You can't set attributes on the built-in date type, so replace the module's name with a small subclass, or use the time-machine library.

time-machine changes the time at the C level, so it also covers libraries you don't control and every way of asking for the time. Add it to your dev dependencies with pixi add --feature dev time-machine.

Randomness

Don't assert on one lucky seed against the global random module, since any other code that draws a number changes your result. Give the code its own generator, random.Random(seed), as a parameter. Then test either exact results from a fixed seed, or properties that hold for any seed.

Remember: pass time and randomness in where you can. Boundaries such as "due today" are where the bugs live, so test them explicitly.

Testing async code

A coroutine test needs an event loop (M38), and plain pytest doesn't provide one. A test declared with async def and no plugin doesn't run its body; pytest reports it as a failure. The usual solution is pytest-asyncio:

pixi add --feature dev pytest-asyncio
[tool.pytest.ini_options]
asyncio_mode = "strict"                         # tests opt in with @pytest.mark.asyncio
asyncio_default_fixture_loop_scope = "function"

For the dependencies themselves, unittest.mock.AsyncMock is a mock whose calls return awaitables. Use assert_awaited_once_with rather than assert_called_once_with, because a coroutine that was called but never awaited did no work. This cell runs in the browser:

The same logic as a real test file, including a timeout check. Timeouts in tests should be tiny: patch the delay down or use a very short limit, so the suite never actually waits.

Remember: mark async tests, use AsyncMock and the assert_awaited_* family, and never let a test really sleep.

Integration tests that clean up after themselves

An integration test uses real resources, so it can also leave real state behind. The next test then fails, or worse, passes only because of what the previous one left. Every integration test must leave the world as it found it.

For a database, the cleanest pattern is to share a schema and wrap each test in a transaction that always rolls back. This is far faster than rebuilding the database per test.

Block the network by default

An accidental real HTTP call makes a suite slow and flaky, and it might even charge a card. A small autouse fixture in the top-level conftest.py turns that mistake into an immediate failure. HTTP code is then tested through the seams from M45: httpx.MockTransport, respx, and FastAPI's TestClient.

Mark integration tests with @pytest.mark.integration and keep them in tests/integration/, so pixi run test stays fast and pixi run cov runs both. Use real infrastructure in these tests rather than mocks; that is the point of them.

Remember: roll back after every test, and make the network an explicit opt-in.

Suite health: speed, flakiness, and quality

Daily commands

pixi run pytest --ff              # run failures first, then everything else
pixi run pytest -k "fee and not negative"   # select by name
pixi run pytest -m "not integration"        # select by mark
pixi run pytest --pdb             # open the debugger at a failure
pixi run pytest --durations=10    # list the 10 slowest tests
pixi run pytest -vv               # show full diffs

Flaky tests

A flaky test passes and fails without any change in the code. Don't just rerun until it goes green, because that teaches the team to ignore red builds. Almost every flaky test has one of a few causes:

CauseSymptomFix
Shared stateFails only after a certain other testFunction-scoped fixtures; monkeypatch rather than direct assignment
Real timeFails at midnight or at month endInject or freeze the clock
Real randomnessFails about one run in a hundredSeeded generator; print the seed on failure
Sleeps and racesFails on a busy CI machineWait on an event, not on a duration
Set or file orderingDiffers per run or per OSSort before comparing
Real networkFails when a service is downThe network guard above

Two plugins expose these problems. pytest-randomly shuffles test order and reseeds random on each run, which reveals hidden order dependence and prints the seed so that you can reproduce it. pytest-xdist runs tests in parallel with -n auto, which speeds up large suites but only works once your tests are truly isolated. Both are on conda-forge: pixi add --feature dev pytest-randomly pytest-xdist.

Coverage measures what ran, not what was checked

This test achieves 100% line coverage of fee and can't fail:

def test_fee_runs():
    fee(0)
    fee(5000)

Coverage finds code that no test touched, which makes it useful for locating gaps but weak as a measure of quality. The stronger question is "if this code broke, would a test fail?" Mutation testing asks exactly that: make a small change to the code, such as >= to >, and see whether the suite notices. A change that survives shows a missing check. Characterization tests for code without tests

When you inherit untested code, you can't write tests from a spec, because the code is the only spec. Write characterization tests instead: run the code, record what it actually does, and pin that behavior with assertions, even the parts that look odd. Then you can refactor safely, and fix bugs as deliberate, visible changes to a test. You will do exactly this in Project 6b.

Remember: treat a flaky test as a bug to diagnose, and trust a suite for the bugs it catches, not for its coverage number.

Practice

Every exercise here runs what you write through real pytest, first against a correct module and then against buggy versions. Your tests must pass on the first and fail on each of the others. Because the checker also runs your code once before pytest does, import the provided modules inside your test functions or fixtures.

Two modules are provided. The real tax_rate raises RuntimeError to stand in for a network call.

# prices.py
def tax_rate(region):
    raise RuntimeError("real network call")

# report.py
from prices import tax_rate

def gross(net, region):
    return round(net * (1 + tax_rate(region)))

Write test_gross. Replace the rate lookup with a fake that returns 0.5 for region "eu" and 0.0 for any other region. Then check that gross(100, "eu") is 150.

Hint

report.py uses from prices import tax_rate, so the name to patch is report.tax_rate. A lambda works: lambda region: 0.5 if region == "eu" else 0.0.

Show solution 
def test_gross(monkeypatch):
    import report
    monkeypatch.setattr(report, "tax_rate", lambda region: 0.5 if region == "eu" else 0.0)
    assert report.gross(100, "eu") == 150

The module syncer is provided:

import logging

logger = logging.getLogger("sync")

def sync(items):
    for item in items:
        if not item:
            logger.warning("skipping empty item")
            continue
        print(f"synced {item}")

Write test_prints_each_item, which checks that sync(["a", "b"]) writes exactly "synced a\nsynced b\n" to standard output. Then write test_warns_on_empty, which checks that sync([""]) logs one WARNING record containing "skipping empty item".

Hint

capsys.readouterr().out gives you the printed text. caplog.records is a list of records with .levelname and .getMessage().

Show solution 
def test_prints_each_item(capsys):
    import syncer
    syncer.sync(["a", "b"])
    assert capsys.readouterr().out == "synced a\nsynced b\n"

def test_warns_on_empty(caplog):
    import syncer
    syncer.sync([""])
    assert [r.levelname for r in caplog.records] == ["WARNING"]
    assert "skipping empty item" in caplog.text

The module registry keeps global state:

USERS = []

def register(name, admin=False):
    user = {"name": name, "admin": admin}
    USERS.append(user)
    return user

Write two fixtures; the checker supplies the tests that use them.

  • fresh_registry: an autouse fixture that gives every test its own empty registry.USERS.
  • make_user: a factory fixture. make_user() registers and returns a user named "ada" who is not an admin, and make_user(name="alan", admin=True) overrides those values.
Hint

Add autouse=True and call monkeypatch.setattr(registry, "USERS", []). For the factory, define an inner function with default arguments and return it without calling it.

Show solution 
import pytest

@pytest.fixture(autouse=True)
def fresh_registry(monkeypatch):
    import registry
    monkeypatch.setattr(registry, "USERS", [])

@pytest.fixture
def make_user():
    import registry
    def _make(name="ada", admin=False):
        return registry.register(name, admin=admin)
    return _make

The module shipping has one function. Shipping is free from 5000 cents upward, costs 499 cents below that, and a negative total raises ValueError.

def fee(cents):
    if cents < 0:
        raise ValueError("negative total")
    return 0 if cents >= 5000 else 499

Write a parametrized test_fee using pytest.param with exactly these ids: empty (0), just-below (4999), and at-threshold (5000). Then write test_negative using pytest.raises.

Hint

pytest.param(5000, 0, id="at-threshold") is one row of the table.

Show solution 
import pytest

@pytest.mark.parametrize(
    "cents, expected",
    [
        pytest.param(0, 499, id="empty"),
        pytest.param(4999, 499, id="just-below"),
        pytest.param(5000, 0, id="at-threshold"),
    ],
)
def test_fee(cents, expected):
    import shipping
    assert shipping.fee(cents) == expected

def test_negative():
    import shipping
    with pytest.raises(ValueError):
        shipping.fee(-1)

The module loans reads the real date, and you may not change it:

from datetime import date

def is_overdue(due):
    return date.today() > due

Write tests that make loans believe today is 2026-03-01. Check that a loan due 2026-02-28 is overdue and that a loan due 2026-03-01 is not. The checker also runs your tests against a copy of the module whose clock reads a different date, so comparing against the real date.today() won't pass.

Hint

Give FrozenDate a today classmethod that returns cls(2026, 3, 1), then call monkeypatch.setattr(module, "date", FrozenDate).

Show solution 
from datetime import date
import pytest

@pytest.fixture
def loans(monkeypatch):
    import loans as module

    class FrozenDate(date):
        @classmethod
        def today(cls):
            return cls(2026, 3, 1)

    monkeypatch.setattr(module, "date", FrozenDate)
    return module

def test_yesterday_is_overdue(loans):
    assert loans.is_overdue(date(2026, 2, 28)) is True

def test_due_today_is_not_overdue(loans):
    assert loans.is_overdue(date(2026, 3, 1)) is False

Quiz

Recap

  • Choose a seam in this order: the real thing if fast, an injected fake if you own the code, monkeypatch for global state, and Mock only when the interaction is the behavior.
  • monkeypatch undoes everything automatically and covers attributes, environment variables, dictionary entries, the working directory, and sys.path.
  • Patch the name where it is looked up. from a import b means you patch your_module.b.
  • capsys, capfd, caplog, and capture_logs each capture a different output path.
  • Factories give variation, autouse enforces safety, params runs contract tests, and the closest conftest.py wins.
  • Pass in time and randomness where possible, and test boundaries explicitly.
  • Async tests need a plugin and assert_awaited_*. Integration tests must roll back. Block the network by default.
  • Diagnose flaky tests rather than rerunning them. Judge a suite by the bugs it catches.
