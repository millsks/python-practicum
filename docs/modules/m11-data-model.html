The Python Data Model

Why does len() work on lists, strings, and dicts alike? Why can you write a + b for numbers and for strings? Because Python's syntax is a set of hooks called special methods. Implement them and your own classes behave exactly like built-ins.

Everything is an object

In Python, every value is an object: a chunk of memory with three properties. Its identity (id(x)) never changes while the object exists. Its type (type(x)) decides which operations it supports. Its value is the data it holds. That includes numbers and strings, but also functions, classes, modules, and even types themselves.

The data model is the part of the language reference that describes how objects plug into Python's syntax. The central idea: syntax calls special methods on the object's type. Special methods have names surrounded by double underscores, like __len__. People call them dunder methods ("double underscore").

Notice "type(x)": special methods are looked up on the class, not the instance. Assigning obj.__len__ = ... on one instance has no effect on len(obj). And you almost never call dunders directly; write len(x), not x.__len__(). The built-in functions do extra work (for example, len checks the result is a non-negative int).

That last line prints NotImplemented: a special singleton value that a binary method returns to say "I don't know how to handle this operand." You will learn exactly what Python does with it in the operator sections.

This uniformity is the reason Python feels consistent. Libraries like NumPy, pandas, and SQLAlchemy feel native (array * 2, df["col"], User.age > 18) because they implement these same hooks. Learning the data model is learning how every serious Python library is built.

Remember: every value is an object, and syntax is a call to a special method on the object's type.

__repr__ and __str__

Without help, your objects print as something like <__main__.Point object at 0x10a3f2d50>. That tells you nothing while debugging. Two methods fix this:

  • __repr__: the developer representation, returned by repr(x). It should be unambiguous, and ideally look like a Python expression that recreates the object: Point(x=1, y=2). The REPL, debuggers, logs, and containers (a list prints the repr of each element) all use it.
  • __str__: the user-facing representation, returned by str(x) and used by print() and f-strings. If you don't define it, Python falls back to __repr__.

Always write __repr__. Only write __str__ when users need a different, friendlier format. Using type(self).__name__ instead of a hard-coded class name makes the repr correct for subclasses too.

Remember: __repr__ is for developers (unambiguous, recreatable); __str__ is for end users and falls back to __repr__.

Equality and hashing: the contract

By default, a == b for your objects is the same as a is b: two separately created points are never equal, even with identical coordinates. Define __eq__ to compare by value:

class Point:
    def __init__(self, x, y):
        self.x, self.y = x, y

    def __eq__(self, other):
        if not isinstance(other, Point):
            return NotImplemented          # let Python try other.__eq__, then fall back to identity
        return (self.x, self.y) == (other.x, other.y)

Returning NotImplemented (not False, and not raising) for unknown types is important: it gives the other operand a chance to answer, and if neither knows, Python falls back to an identity check, so Point(1, 2) == "hello" is simply False. You also get != for free: the default __ne__ inverts __eq__.

Why __hash__ must follow

Dictionaries and sets find keys by their hash: an integer computed by hash(x) that decides which bucket to look in (you will build a hash table in Part 3). The lookup first jumps to the bucket by hash, then confirms with ==. This only works if Python can rely on the hash contract:

If a == b, then hash(a) == hash(b) must be true. (Unequal objects may share a hash; that is a collision, which is allowed but slower.) And an object's hash must never change while it is in a set or dict, so hashable objects should be immutable in every field that takes part in equality.

To protect you, Python sets __hash__ = None automatically when a class defines __eq__ without __hash__. Instances become unhashable: putting them in a set raises TypeError. That is a deliberate safety net, not a bug. Step through the trace to see a set lookup succeed only after both methods are defined consistently:

The idiomatic hash combines exactly the fields used in __eq__ into a tuple and hashes that. The fields are stored as _x/_y (with no setters) to signal that they must not change.

Remember: define __eq__ and __hash__ together, hash the same fields you compare, keep those fields immutable, and return NotImplemented for unknown types.

Ordering and functools.total_ordering

sorted(), min(), max(), and comparisons like a < b use the rich comparison methods: __lt__ (<), __le__ (<=), __gt__ (>), and __ge__ (>=). Writing all four is repetitive and error-prone. The functools.total_ordering class decorator fills in the rest if you supply __eq__ and one ordering method.

Two lessons hide here. First, comparing as tuples of ints gives the right answer (3.9 < 3.13), while comparing the strings would not ("3.9" > "3.13"). Second, returning NotImplemented for an unknown type lets Python try the reflected comparison ("2.0".__gt__(v)); when that is also NotImplemented, Python raises a clear TypeError.

Often you don't need ordering methods at all: sorted(items, key=lambda v: v.parts) sorts by a key without changing the class. Implement ordering when the type has one obvious natural order. @dataclass(order=True) (M13) can also generate it.

Remember: supply __eq__ plus __lt__ and decorate with @total_ordering; compare tuples of fields; return NotImplemented for foreign types.

Arithmetic operators and reflected operations

Operator overloading means defining what +, -, *, and friends do for your type. Each binary operator has three methods:

OperatorNormalReflected (right side)In-place
+__add____radd____iadd__ (+=)
-__sub____rsub____isub__
*__mul____rmul____imul__
/__truediv____rtruediv____itruediv__
@__matmul____rmatmul____imatmul__

Unary operators have single methods: __neg__ (-v), __pos__, __abs__ (abs(v)).

How Python evaluates a + b

  1. Call type(a).__add__(a, b). If it returns a value other than NotImplemented, that is the result.
  2. Otherwise call type(b).__radd__(b, a), the reflected method. If it returns a real value, done.
  3. If both return NotImplemented (or don't exist), raise TypeError: unsupported operand type(s).

(One refinement: if b's type is a subclass of a's type and overrides the reflected method, Python tries b's reflected method first, so subclasses can take control.)

This is why 3 * v can work for your vector: int.__mul__(3, v) has no idea what a vector is and returns NotImplemented, so Python asks v.__rmul__(3).

Here is a complete, well-behaved Vector2. Experiment with it: try v - "x", abs(v), and v += w.

Look at the += line. Without __iadd__, Python computes v + w and rebinds v to the new object, leaving alias pointing at the old one. Mutable built-ins such as list define __iadd__ to mutate in place (and return self), which is why += on a list affects every alias. For value-like types, not defining __iadd__ is usually the safer choice.

Returning NotImplemented and raising NotImplementedError are different things. NotImplemented is a value that operator methods return to let Python try the other operand. NotImplementedError is an exception you raise in a method that a subclass must override (M12). Raising it from __add__ would block the reflected method.

Remember: a + b tries a.__add__(b), then b.__radd__(a); return NotImplemented for types you don't support; += falls back to + and rebinding.

The sequence and container protocols

A protocol in Python is an informal set of methods that, when present, let an object work in a certain context. You don't inherit from anything; you just implement the methods. This is duck typing: "if it walks like a duck and quacks like a duck, it's a duck." (M12 shows how to formalize protocols with typing.Protocol.)

MethodEnablesFallback when missing
__len__len(x), truthinessTypeError
__getitem__x[i], x[a:b], x["key"]TypeError
__iter__for, list(x), unpackingcalls __getitem__(0), (1), … until IndexError
__contains__item in xiterates and compares with ==
__reversed__reversed(x)uses __len__ + __getitem__

The fallbacks are generous: a class with just __len__ and __getitem__ is already iterable, supports in, and works with reversed(). You add __iter__ and __contains__ when you can do them more efficiently or more correctly.

__getitem__ receives whatever is inside the brackets. For deck[1:5] that is a slice object, slice(1, 5, None); because we delegate to a list, slicing works automatically. If you want slices to return your own type rather than a list, check isinstance(position, slice) and wrap the result.

For mappings, __getitem__ takes keys instead of positions, and should raise KeyError for a missing key (sequences raise IndexError). Those exception types matter: the iteration fallback stops on IndexError, and dict.get-style code catches KeyError.

When you want a complete, correct container, inherit from the abstract base classes in collections.abc (such as Sequence or Mapping). You implement two or three core methods, and the ABC supplies index, count, __contains__, __iter__, __reversed__, keys, items, and more. M12 covers ABCs.

Remember: __len__ + __getitem__ gets you a lot; add __iter__ and __contains__ for efficiency; raise IndexError for sequences and KeyError for mappings.

Truthiness with __bool__

Every object can be tested in if, while, and, or, and not. Python decides its truth value in this order:

  1. If the type defines __bool__, call it. It must return True or False.
  2. Otherwise, if it defines __len__, the object is false when the length is 0.
  3. Otherwise the object is always true.

That's why empty lists, strings, and dicts are falsy: they define __len__. Your Deck above is falsy once empty, with no extra work.

Be careful with if obj: when obj might be None or a legitimately empty value. if result: treats an empty container the same as None. When you mean "was a value provided?", write if result is not None:.

Remember: __bool__ first, then __len__, then always true.

Callable objects and context managers (preview)

__call__

Functions are objects whose type defines __call__. Your own objects can be callable too. This is useful when you need a function that remembers state or is configured once and used many times:

Anything that accepts a function (like key= for sorted, or callbacks) accepts a callable object. In M15 you will see closures, which are often a lighter-weight alternative.

__enter__ and __exit__

You have used with open(...) as f: since M09. The with statement is another protocol: it calls __enter__ at the start (its return value is bound by as), and __exit__(exc_type, exc, tb) at the end, even if an exception was raised. If __exit__ returns a true value, the exception is suppressed; normally it returns None/False so errors propagate.

M15 goes deeper, including contextlib.contextmanager, which builds context managers from generators.

Remember: __call__ makes instances callable; __enter__/__exit__ power with, and __exit__ always runs.

Hint

Show solution 
from functools import total_ordering

@total_ordering
class Version:
    def __init__(self, text):
        self.parts = tuple(int(p) for p in text.split("."))

    def __repr__(self):
        return f"Version({'.'.join(map(str, self.parts))!r})"

    def __eq__(self, other):
        if not isinstance(other, Version):
            return NotImplemented
        return self.parts == other.parts

    def __hash__(self):
        return hash(self.parts)

    def __lt__(self, other):
        if not isinstance(other, Version):
            return NotImplemented
        return self.parts < other.parts

Show solution 
import math

class Vector2:
    def __init__(self, x, y):
        self.x = x
        self.y = y

    def __repr__(self):
        return f"Vector2({self.x!r}, {self.y!r})"

    def __eq__(self, other):
        if not isinstance(other, Vector2):
            return NotImplemented
        return (self.x, self.y) == (other.x, other.y)

    __hash__ = None

    def __add__(self, other):
        if not isinstance(other, Vector2):
            return NotImplemented
        return Vector2(self.x + other.x, self.y + other.y)

    def __sub__(self, other):
        if not isinstance(other, Vector2):
            return NotImplemented
        return Vector2(self.x - other.x, self.y - other.y)

    def __mul__(self, k):
        if not isinstance(k, (int, float)):
            return NotImplemented
        return Vector2(self.x * k, self.y * k)

    __rmul__ = __mul__

    def __neg__(self):
        return Vector2(-self.x, -self.y)

    def __abs__(self):
        return math.hypot(self.x, self.y)

Implement __len__ (number of words), __getitem__ (indexing and slicing: a slice returns a new Sentence of those words), __iter__ (yields words), __contains__ (case-insensitive word membership), __bool__ (false when there are no words), and __repr__ returning Sentence('the words').

Show solution 
class Sentence:
    def __init__(self, text):
        self.words = text.split()

    def __repr__(self):
        return f"Sentence({' '.join(self.words)!r})"

    def __len__(self):
        return len(self.words)

    def __getitem__(self, index):
        if isinstance(index, slice):
            return Sentence(" ".join(self.words[index]))
        return self.words[index]

    def __iter__(self):
        return iter(self.words)

    def __contains__(self, word):
        target = word.lower()
        return any(w.lower() == target for w in self.words)

    def __bool__(self):
        return bool(self.words)

Write Polynomial(*coeffs) where coefficients are given from the constant term upward: Polynomial(1, 0, 2) means 1 + 0x + 2x². Implement __call__(x) to evaluate it, __add__ for two polynomials (pad the shorter one with zeros), __eq__ (compare coefficients after dropping trailing zeros), and __bool__ (false for the zero polynomial).

Hint

Normalize in __init__: convert to a list and pop trailing zeros. Then equality is plain list comparison and __bool__ is bool(self.coeffs). Evaluate with sum(c * x ** i for i, c in enumerate(self.coeffs)).

Show solution 
from itertools import zip_longest

class Polynomial:
    def __init__(self, *coeffs):
        self.coeffs = list(coeffs)
        while self.coeffs and self.coeffs[-1] == 0:
            self.coeffs.pop()

    def __repr__(self):
        return f"Polynomial{tuple(self.coeffs)!r}"

    def __call__(self, x):
        return sum(c * x ** i for i, c in enumerate(self.coeffs))

    def __add__(self, other):
        if not isinstance(other, Polynomial):
            return NotImplemented
        return Polynomial(*(a + b for a, b in zip_longest(self.coeffs, other.coeffs, fillvalue=0)))

    def __eq__(self, other):
        if not isinstance(other, Polynomial):
            return NotImplemented
        return self.coeffs == other.coeffs

    __hash__ = None

    def __bool__(self):
        return bool(self.coeffs)

Mini-project: a currency-safe Money type

Mini-projectMoney with currency-safe arithmetic

Floating-point dollars and silent currency mix-ups cause real financial bugs. Build an immutable Money value type that behaves like a number but refuses to add euros to dollars.

Specification

  • Money(amount, currency) stores the amount as decimal.Decimal (accept str, int, or Decimal; reject float with TypeError to avoid rounding surprises), quantized to two decimal places, and the currency as an uppercase 3-letter code.
  • Read-only properties amount and currency; no setters (the type is immutable).
  • __repr__ → Money('12.50', 'USD'); __str__ → 12.50 USD.
  • __eq__ and __hash__ on (amount, currency), so Money works as a dict key.
  • @total_ordering with __lt__ that raises ValueError for different currencies.
  • + and - between Money of the same currency; different currencies raise a custom CurrencyMismatchError; any other type returns NotImplemented.
  • * by an int or Decimal on either side (__mul__ and __rmul__); unary -; abs(); __bool__ false for zero.
  • sum(wallet, start=Money(0, "USD")) works.
  • allocate(ratios) splits money into parts that add up exactly to the original (for example, 100.00 split 1:1:1 is 33.34, 33.33, 33.33).

Acceptance criteria

  • Money("0.10", "usd") + Money("0.20", "USD") == Money("0.30", "USD") is True
  • Money("1", "USD") + Money("1", "EUR") raises CurrencyMismatchError
  • Money("1", "USD") + 1 raises TypeError (because __add__ returned NotImplemented)
  • 3 * Money("1.50", "USD") and Money("1.50", "USD") * 3 both give 4.50 USD
  • Money values can be dict keys and set members, and assigning m.amount = ... raises AttributeError
  • sorted() works for a list of one currency
  • The parts from allocate always sum to the original amount

Stretch goals

  • Add __format__ so f"{m:,}" prints thousands separators.
  • Add __truediv__ for Money / Money (a ratio) and Money / int (a Money), rejecting Money / Money of different currencies.
  • Write pytest tests for each criterion (pixi add pytest, then pixi run pytest); you will learn pytest fully in M17.
