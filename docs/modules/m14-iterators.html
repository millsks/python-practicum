Iterators & Generators

The for loop is the most-used statement in Python, and behind it sits one tiny protocol. Once you understand it, you can process a 50 GB log file in constant memory, describe infinite sequences, and chain data transformations into clean, lazy pipelines.

Iterables and iterators

Two words that sound alike mean different things, and keeping them apart is the key to this module.

  • An iterable is anything you can loop over: lists, strings, dicts, sets, files, range objects. Technically, an object is iterable if iter(obj) works, which means its type defines __iter__ (or the older __getitem__ fallback from M11).
  • An iterator is the object that does the actual stepping. It remembers a position and hands out one item each time you call next() on it, raising StopIteration when it's exhausted. Its type defines __next__, and its __iter__ returns itself.

An analogy: a book is an iterable; a bookmark is an iterator. Many readers can each have their own bookmark in the same book, and a bookmark only moves forward.

The exhaustion trap

A list can be looped over any number of times, because each loop calls iter() and gets a fresh iterator. An iterator, once consumed, stays empty. Many built-ins return iterators (map, filter, zip, enumerate, reversed, file objects, generators), so this surprises everyone at least once:

If a function needs to loop over its argument more than once, either accept a Sequence (list, tuple) or convert once at the top: items = list(items). Otherwise a caller passing a generator gets silently wrong results on the second pass.

Remember: an iterable can produce iterators; an iterator produces items, once, until StopIteration.

The for loop, desugared

"Syntactic sugar" is syntax that is shorthand for something longer. The for loop is sugar for a while loop over an iterator. These two programs do exactly the same thing:

for item in iterable:
    body(item)
_it = iter(iterable)
while True:
    try:
        item = next(_it)
    except StopIteration:
        break
    body(item)

This is the whole iterator protocol: __iter__ to get an iterator, __next__ to get items, StopIteration to finish. Every consumer of iterables, including list(), sum(), sorted(), in, unpacking (a, b = pair), *args, comprehensions, and str.join, speaks this same protocol. So any object you make iterable works with all of them.

Remember: for calls iter() once, then next() repeatedly until StopIteration.

Generator functions and yield

A generator function is any function whose body contains yield. Calling it does not run the body. Instead it returns a generator: an iterator that runs the body lazily. Each next() runs the code until the next yield, hands out the yielded value, and then pauses, freezing the function's local variables and position. The next next() resumes right after the yield. When the function returns, the generator raises StopIteration.

Remember: calling a generator function returns a paused generator; each next() runs to the next yield; locals survive between steps.

Generator expressions and memory

A generator expression is a comprehension in parentheses: (n * n for n in nums). It produces a generator instead of a list. When it's the only argument to a function, the extra parentheses can be dropped: sum(n * n for n in nums).

The difference is memory. A list comprehension builds every element at once; a generator expression stores only its current state, regardless of how many items it will produce.

sys.getsizeof reports only the container itself; the million int objects the list points to take tens of megabytes more. The generator's size is the same for ten items or ten billion.

any stops at the first true value, and because the generator is lazy, check(5) and check(7) never run. With a list comprehension inside any([...]), all four checks would run first.

Remember: parentheses make it lazy and constant-memory; use generator expressions for single-pass consumers.

yield from, send, and close

Delegating with yield from

yield from iterable yields every item of another iterable, as if you'd written for x in iterable: yield x. With a sub-generator it does more: it passes send() and close() through, and its value is the sub-generator's return value. It's the natural tool for recursive generators, such as walking a tree:

send() and close() (briefly)

A yield is also an expression: received = yield value. Calling gen.send(x) resumes the generator and makes that yield evaluate to x. (next(gen) is the same as gen.send(None).) You must start a generator with next() before you can send to it. gen.close() raises GeneratorExit at the paused yield so finally blocks run and resources are released.

Generators that receive values this way were the foundation of Python's early coroutines. Modern asynchronous code uses async def and await instead, which you'll meet in Part 4. Day to day, you'll use yield and yield from constantly and send rarely.

Remember: yield from delegates to another iterable (and returns a sub-generator's result); send passes values in; close triggers cleanup.

Infinite generators and lazy pipelines

Because generators produce values on demand, they can describe sequences with no end. The consumer decides when to stop, usually with itertools.islice, a break, or a function like next or any.

Pipelines over big files

The real professional payoff is processing data that doesn't fit in memory. A file object is already a lazy iterator over lines. Chain generator stages, each taking an iterator and yielding transformed items, and the whole pipeline holds just one line at a time, whether the file has 100 lines or 100 million.

def read_lines(path):
    with open(path, encoding="utf-8") as f:   # the file closes when the generator finishes
        for line in f:                          # one line in memory at a time
            yield line.rstrip("\n")

def parse(lines):
    for line in lines:
        level, _, message = line.partition(" ")
        yield {"level": level, "message": message}

def errors_only(records):
    return (r for r in records if r["level"] == "ERROR")

# Nothing is read until the final consumer pulls values through:
pipeline = errors_only(parse(read_lines("app.log")))
print(sum(1 for _ in pipeline))

Remember: infinite generators are fine because consumers stop them; chain generator stages for constant-memory processing of any amount of data.

The itertools toolkit

The standard library's itertools module is a set of fast, memory-efficient building blocks for iterators, implemented in C. Learning them saves you from writing (and debugging) your own loops.

groupby is not SQL's GROUP BY. It groups runs of consecutive equal keys, so unsorted input produces repeated groups. Sort by the same key first, or use a dict (collections.defaultdict(list)) when you don't need streaming. Also, each group is a sub-iterator that is invalidated when groupby advances; convert it with list(g) immediately if you need to keep it.

Remember: reach for itertools before writing a loop; groupby needs sorted input.

Strictness: zip, batched, and map

Lazy tools have one dangerous default: when input lengths don't line up, they quietly stop or produce a short final chunk. zip(names, scores) silently drops extra names if scores is shorter, hiding a data bug. Modern Python adds strict=True options that turn the mismatch into a ValueError:

  • zip(a, b, strict=True) (3.10+): raise if the iterables have different lengths.
  • itertools.batched(it, n, strict=True) (3.13+): raise if the final batch is incomplete.
  • map(func, a, b, strict=True) (3.14+): raise if the iterables have different lengths.

Python 3.14 adds strict=True to map(), matching zip(). Previously, a multi-argument map stopped silently at the shortest input.

Use strict=True whenever the inputs are supposed to line up, such as parallel columns, keys and values, or fixed-size records. It costs nothing and catches data bugs at the point they occur. Many teams enforce it with the ruff rule B905 (zip() without an explicit strict=).

Remember: pass strict=True to zip, batched (3.13+), and map (3.14+) when lengths must match.

Practice

Write an iterator class Steps(start, stop, step) that behaves like range for positive steps but also works with floats: it yields start, start + step, … while the value is less than stop. Compute each value as start + i * step (not by repeated addition) to avoid accumulating floating-point error. Raise ValueError in __init__ if step <= 0.

Hint

Keep a counter self._i. In __next__, compute value = self.start + self._i * self.step; if value >= self.stop, raise StopIteration.

Show solution 
class Steps:
    def __init__(self, start, stop, step):
        if step <= 0:
            raise ValueError("step must be positive")
        self.start = start
        self.stop = stop
        self.step = step
        self._i = 0

    def __iter__(self):
        return self

    def __next__(self):
        value = self.start + self._i * self.step
        if value >= self.stop:
            raise StopIteration
        self._i += 1
        return value

Write an infinite generator collatz(n) that yields n, then the next Collatz value (n // 2 if even, else 3 * n + 1), forever. Then write take(n, iterable) returning a list of the first n items (use itertools.islice), and collatz_length(n) returning how many values the sequence has up to and including the first 1.

Hint

For collatz_length, loop over enumerate(collatz(n), start=1) and return the count when the value is 1.

Show solution 
from itertools import islice


def collatz(n):
    while True:
        yield n
        n = n // 2 if n % 2 == 0 else 3 * n + 1


def take(n, iterable):
    return list(islice(iterable, n))


def collatz_length(n):
    for count, value in enumerate(collatz(n), start=1):
        if value == 1:
            return count

Write a generator windows(iterable, size) that yields tuples of size consecutive items: windows([1, 2, 3, 4], 3) yields (1, 2, 3) and (2, 3, 4). It must work on any iterable, including infinite generators, using constant memory (use collections.deque(maxlen=size)). Then write moving_average(values, size) as a generator of window averages.

Hint

Append each item to a deque(maxlen=size); once len(window) == size, yield tuple(window).

Show solution 
from collections import deque


def windows(iterable, size):
    window = deque(maxlen=size)
    for item in iterable:
        window.append(item)
        if len(window) == size:
            yield tuple(window)


def moving_average(values, size):
    for w in windows(values, size):
        yield sum(w) / size

Write a generator flatten(obj) that yields every leaf of arbitrarily nested lists, tuples, and sets, using yield from for the recursion. Strings and bytes must be treated as leaves (not split into characters), as must dicts.

Hint

If obj is a list, tuple, or set, loop over it and yield from flatten(item); otherwise yield obj.

Show solution 
def flatten(obj):
    if isinstance(obj, (list, tuple, set)):
        for item in obj:
            yield from flatten(item)
    else:
        yield obj

Build three generator stages and a consumer. Lines look like "2026-10-01T12:00:00 ERROR db timeout" (timestamp, level, message, separated by single spaces; the message may contain spaces).

  • parse(lines): skip blank lines and lines starting with #; yield tuples (timestamp, level, message).
  • at_least(records, level): yield records whose level is at or above level in the order DEBUG < INFO < WARN < ERROR.
  • messages(records): yield just the messages.
  • count_levels(records): return a dict of level counts (this one consumes).

The stages must be lazy: they must not read more input than needed.

Hint

line.split(" ", 2) splits into at most three parts. Compare levels with LEVELS.index(r[1]) >= LEVELS.index(level).

Show solution 
LEVELS = ["DEBUG", "INFO", "WARN", "ERROR"]


def parse(lines):
    for line in lines:
        line = line.strip()
        if not line or line.startswith("#"):
            continue
        timestamp, level, message = line.split(" ", 2)
        yield timestamp, level, message


def at_least(records, level):
    threshold = LEVELS.index(level)
    for record in records:
        if LEVELS.index(record[1]) >= threshold:
            yield record


def messages(records):
    for _, _, message in records:
        yield message


def count_levels(records):
    counts = {}
    for _, level, _ in records:
        counts[level] = counts.get(level, 0) + 1
    return counts

Using itertools, write rle_encode(text) returning a list of (char, count) pairs for consecutive runs ("aaabcc" → [("a", 3), ("b", 1), ("c", 2)]), and rle_decode(pairs) returning the original string. Use groupby for encoding and chain.from_iterable with repeat for decoding.

Hint

Encode: [(ch, len(list(group))) for ch, group in groupby(text)]. Decode: "".join(chain.from_iterable(repeat(ch, n) for ch, n in pairs)).

Show solution 
from itertools import groupby, chain, repeat


def rle_encode(text):
    return [(ch, sum(1 for _ in group)) for ch, group in groupby(text)]


def rle_decode(pairs):
    return "".join(chain.from_iterable(repeat(ch, n) for ch, n in pairs))

Mini-project: a log-processing pipeline

Mini-projectStreaming log analyzer

Build a command-line tool that analyzes web-server logs of any size in constant memory, using only generators and itertools. Then prove it: generate a log with a million lines and watch memory stay flat.

pixi init logpipe
cd logpipe
mkdir -p src
pixi run python src/make_logs.py 1000000 > big.log      # step 1: a generator that writes fake logs
pixi run python src/logpipe.py big.log --level WARN --top 5

Specification

  • make_logs.py: an infinite generator of realistic lines (timestamp level path status latency_ms), sliced with islice to the requested count and written line by line.
  • read_lines(paths): yields lines from one or more files, chained with yield from; transparently opens .gz files with gzip.open(path, "rt").
  • parse(lines): yields LogRecord NamedTuples (or frozen dataclasses from M13); counts and skips malformed lines instead of crashing.
  • filter_level(records, minimum) and between(records, start, end) stages.
  • per_minute(records): uses groupby on the timestamp truncated to the minute (logs are already in time order) to yield (minute, count, error_rate).
  • top_paths(records, n): the n slowest paths by average latency (this stage may hold one dict of per-path totals, but never the records).
  • batched(records, 1000) to "upload" results in chunks (just count the batches).
  • main() parses arguments with argparse and prints a short report.

Acceptance criteria

  • Every stage is a generator (or a consumer that iterates once); no stage calls list() on the full stream
  • Processing a million-line file keeps memory roughly constant (check with /usr/bin/time -l on macOS or /usr/bin/time -v on Linux, or tracemalloc)
  • Malformed lines are counted and reported, not fatal
  • --head 10 stops reading the file after the first 10 matching records (use islice)
  • Each stage has a small test that feeds it a plain list (run with pixi run pytest after pixi add pytest)
  • All zip/map calls over parallel data use strict=True

Stretch goals

  • Add a --follow mode that tails a growing file forever (an infinite generator that sleeps and retries at end of file).
  • Support compressed input with compression.zstd (new in 3.14) as well as gzip.
  • Compare the speed and memory of your generator pipeline against loading everything into pandas.

Quiz

Recap

  • An iterable gives iterators (__iter__); an iterator gives items (__next__) and raises StopIteration.
  • for x in it = iter() once, then next() until StopIteration.
  • Iterators are single-use; containers should return a fresh iterator from __iter__.
  • Generator functions (yield) pause and resume, keeping their locals; calling one runs nothing yet.
  • Generator expressions are lazy and constant-memory, ideal for one-pass consumers.
  • yield from delegates; send passes values in; close runs cleanup.
  • Infinite generators are safe; consumers decide when to stop. Chain stages for big-data pipelines.
  • itertools provides count, cycle, islice, chain, groupby (sorted input!), accumulate, pairwise, batched, product, permutations, combinations.
  • Use strict=True with zip, batched (3.13+), and map (3.14+).
