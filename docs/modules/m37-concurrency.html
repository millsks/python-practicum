Concurrency: Threads, Processes & Interpreters

Python 3.14 gives you more ways to do several things at once than any previous release: threads, processes, subinterpreters with their own GIL, and an officially supported free-threaded build with no GIL at all. Each has a different cost model. This module explains the machinery underneath so you can pick the right tool, predict its performance, and avoid the bugs that come with shared state.

Concurrency, parallelism, and the shape of your workload

Concurrency is about structure: a program has several tasks in progress at the same time, and their steps interleave. Parallelism is about execution: several steps literally run at the same instant on different CPU cores. A single-core machine can run a concurrent program (by switching between tasks) but cannot run it in parallel. Rob Pike's summary: concurrency is dealing with lots of things at once; parallelism is doing lots of things at once.

Which one you need depends on where your program spends its time:

I/O-bound

Most time is spent waiting: for the network, a disk, a database, a subprocess. The CPU is idle. Concurrency helps enormously, because while one task waits, another can run. You don't need more cores; you need to stop waiting serially. Tools: threads, asyncio (M38).

CPU-bound

Most time is spent computing: parsing, compressing, numeric loops, image processing. Interleaving tasks on one core gains nothing (it adds switching overhead). You need parallelism: more cores executing Python bytecode simultaneously. Tools: processes, subinterpreters, free-threaded Python, or native code that releases the GIL (NumPy).

Before parallelizing, estimate the ceiling. Amdahl's law says that if a fraction p of the runtime can be parallelized across n workers, the best possible speedup is 1 / ((1 - p) + p / n). The serial part dominates quickly: with 90% parallel code, even infinite cores give at most 10×.

Real speedups are lower still, because parallel workers pay coordination costs: starting workers, copying data to them, waiting for locks, and combining results. A recurring theme of this module is that each tool sits at a different point on the trade-off between isolation (safety, but expensive data transfer) and sharing (cheap data access, but you must synchronize).

Your web scraper downloads 500 pages, then parses each one (5 ms of CPU per page). Downloads take 300 ms each. Which part is I/O-bound, which is CPU-bound, and which tool would you use for each? Keep your answer in mind for the decision table at the end.

The GIL, explained

CPython manages memory with reference counting: every object has a counter of how many references point at it, and the object is freed when it drops to zero. Incrementing and decrementing those counters happens constantly, on every assignment and function call. If two threads updated the same counter at once without synchronization, counts would be corrupted and objects freed while still in use.

The classic solution is the Global Interpreter Lock (GIL): one mutex per interpreter that a thread must hold to execute Python bytecode or touch Python objects. It makes reference counting and the internals of dict, list, and friends safe without fine-grained locks, and makes single-threaded code fast. The cost: in a standard build, only one thread executes Python bytecode at a time, so threads never speed up pure-Python CPU work.

Threads still help with I/O because the GIL is released at the right moments:

  • Blocking system calls: socket reads, file I/O, time.sleep, waiting on a lock or a subprocess. The thread drops the GIL while the OS does the waiting.
  • C extensions that opt in: NumPy's large array operations, hashlib on big buffers, zlib/compression.zstd, many image libraries. Their inner loops don't touch Python objects, so they run in parallel with other threads.
  • Periodically: a thread running pure Python is asked to drop the GIL every switch interval (5 ms by default, see sys.getswitchinterval()) so other threads get a turn. This is why threads are preemptive: a switch can happen between almost any two bytecode instructions.

That last point is the root of race conditions. The GIL makes individual bytecode instructions atomic, but a line like counter += 1 compiles to several instructions: load, add, store. A switch between the load and the store loses an update.

A thread switch after LOAD_GLOBAL counter but before STORE_GLOBAL counter lets another thread read the same old value. Both store old + 1, and one increment vanishes. In a GIL build this is rare for such a tiny window (and recent CPython versions make it rarer still), which is exactly what makes it dangerous: tests pass, production loses data. In a free-threaded build it happens constantly.

The GIL never made your code thread-safe. It protects the interpreter's internals, not your program's invariants. Any read-modify-write on shared state ("check balance, then withdraw", "if key not in cache: compute and store") needs a lock, a queue, or a design that avoids sharing.

Threads and race conditions

A thread is an independent flow of execution inside one process. All threads share the same memory: the same modules, globals, and objects. That makes communication free and bugs easy. The threading module wraps the operating system's threads (each Python thread is a real OS thread).

Deadlock: thread A holds lock 1 and waits for lock 2 while thread B holds lock 2 and waits for lock 1. Neither can proceed. Prevent it by always acquiring locks in one global order, holding locks for as short a time as possible, never calling unknown code (callbacks, I/O) while holding a lock, and using lock.acquire(timeout=...) in code that must not hang forever.

Remember: threads share memory; any compound operation on shared state needs a critical section. Prefer designs that share less (next section) over designs with more locks.

Producer/consumer with queue.Queue

The safest way to share data between threads is to not share it: pass it. queue.Queue is a thread-safe FIFO with the locking done for you. Producers put() work items; consumers get() them. A maxsize gives back-pressure: when the queue is full, producers block instead of piling up unbounded memory. task_done() and join() let the main thread wait until every item has been processed, and a sentinel (often None) tells consumers to exit.

Pair every get() with exactly one task_done() in a finally block. A missing task_done() makes join() hang forever, which is the single most common queue bug (you will meet its asyncio twin in Project 5).

concurrent.futures: executors and futures

Managing threads by hand is verbose. concurrent.futures provides one interface over three kinds of worker pools: ThreadPoolExecutor, ProcessPoolExecutor, and (new in 3.14) InterpreterPoolExecutor. You submit callables and get back futures: placeholder objects for a result that doesn't exist yet.

  • executor.submit(fn, *args) returns a Future. future.result(timeout=None) blocks until it's done and returns the value or re-raises the worker's exception.
  • executor.map(fn, iterable) returns results in input order (lazily).
  • as_completed(futures) yields futures as they finish, which is best for progress bars and for acting on fast results first.
  • wait(futures, return_when=FIRST_EXCEPTION) gives you (done, not_done) sets.
  • with Executor(...) as ex: calls shutdown(wait=True) on exit; shutdown(cancel_futures=True) drops pending work.

Size pools deliberately. For CPU-bound pools, more workers than cores only adds overhead (os.process_cpu_count(), new in 3.13, respects CPU affinity). For I/O-bound thread pools the right size depends on what you're waiting for: the server's rate limits and your connection limit matter more than your core count.

multiprocessing: true parallelism with isolation

A process has its own memory space and its own interpreter (and so its own GIL). Running Python in several processes gives real CPU parallelism on a standard build. The price is isolation: processes don't share objects, so arguments and results must be serialized with pickle, sent through a pipe, and deserialized on the other side. That means:

  • Functions and arguments must be picklable. Module-level functions pickle (by reference to their qualified name); lambdas, nested functions, open files, sockets, and locks don't.
  • Sending large data is expensive. Parallelizing a task that takes 1 ms but ships 10 MB is a slowdown.
  • Workers must be able to import your function, which is why the if __name__ == "__main__": guard is mandatory with the spawn and forkserver start methods. Without it, each child re-runs your script's top level as it imports it.

Start methods

How a child process is created matters for speed, safety, and what state it inherits:

MethodHowProsConsDefault on
forkCopy the parent process (copy-on-write)Fast start; child inherits everythingUnsafe with threads: locks held by other threads are copied in a locked state; can deadlock or crashnone since 3.14
spawnStart a fresh interpreter, import the main moduleClean, safe, portableSlowest start; everything is pickledWindows, macOS
forkserverA clean single-threaded server process forks children on requestFast-ish and thread-safePOSIX only; still pickles argumentsLinux (and other POSIX except macOS) 3.14

Python 3.14 changed the default start method on Linux from fork to forkserver, because forking a process that has threads (very common once libraries start background threads) is a source of rare, nasty deadlocks. Code that relied on fork inheriting global state (for example passing a lambda or a module-level object set up after import) may break; fix it by passing data explicitly or, if you must, by choosing a context: multiprocessing.get_context("fork").

Sharing memory instead of copying it

For big numeric data, pickling every chunk is wasteful. multiprocessing.shared_memory.SharedMemory creates a named block of memory that several processes map; wrap it in a NumPy array and workers read and write the same bytes with no copying. You are back to shared state, so coordinate writes (each worker owns a slice, or use a multiprocessing.Lock). Simpler options: multiprocessing.Value/Array for small typed buffers, and Manager() for proxied dicts and lists (convenient but slow: every access is an IPC round-trip).

Free-threaded Python 3.14: no GIL

PEP 703 introduced an optional CPython build without the GIL in 3.13 (experimental). In 3.14, PEP 779 promoted it to officially supported (phase II): it is a separate build you choose, not the default. In this build, threads run Python bytecode truly in parallel on multiple cores. To make that safe, CPython uses biased reference counting (cheap counts for the owning thread, atomic ones for others), immortal objects (like None and small ints, whose counts never change), per-object locks inside built-in containers, and a thread-safe memory allocator (mimalloc).

The interpreter binary is conventionally called python3.14t (the t stands for "threaded"). You can tell which build you're on, and whether the GIL is actually off right now:

On conda-forge, the free-threaded interpreter is provided through the python-freethreading package. In a Pixi workspace (ideally in its own feature/environment so your main environment keeps the standard build):

pixi add --feature ft python-freethreading      # check availability first: pixi search python-freethreading
pixi workspace environment add ft --feature ft
pixi run -e ft python -c "import sys; print(sys._is_gil_enabled())"   # expect False

Package names and pins on conda-forge can change, so confirm with pixi search and always verify the result with sys._is_gil_enabled() rather than trusting the environment name.

The GIL can come back. If you import a C extension that hasn't declared itself free-threading compatible, the interpreter re-enables the GIL (and warns) to stay safe. You can force the choice with the environment variable PYTHON_GIL=0 or PYTHON_GIL=1, or with -X gil=0. Most of the scientific stack (NumPy, SciPy, and others) publishes free-threaded builds, but check each dependency.

Thread safety without a GIL

Free threading doesn't change Python's semantics, but it removes the accidental protection many programs relied on. What still holds and what doesn't:

OperationFree-threaded behavior
Single operations on built-ins (list.append, dict[k] = v, d.get(k))Safe: internally locked per object; no crashes or corruption
Compound operations (x += 1, if k not in d: d[k] = ..., iterate-while-mutating)Racy, and now races happen often. Use a lock or an atomic design.
Sharing one iterator or generator between threadsNot safe; give each thread its own
queue.Queue, threading primitives, concurrent.futuresDesigned for this; your best tools
Your own classes with mutable stateAs unsafe as they always were, minus the luck

Performance expectations

  • Single-threaded code is somewhat slower on the free-threaded build (the 3.14 docs put the overhead at roughly 5–10% for typical code, down from much higher in 3.13), because of atomic reference counts and fine-grained locking. Some specializations of the adaptive interpreter are also more limited.
  • CPU-bound multi-threaded Python code scales with cores, which is the whole point: n threads on n cores can approach n× for embarrassingly parallel work.
  • Contention kills scaling: threads hammering one shared dict, list, or lock serialize on its per-object lock. Partition data so each thread works on its own objects and combine at the end.
  • Memory use is somewhat higher, and extensions that re-enable the GIL silently remove all the gains. Measure on your workload with the benchmark in the mini-project.

Looking ahead: a major obstacle for free threading is that C extensions must be compiled separately for the free-threaded ABI (the cp314t wheel tag) because the limited/stable ABI (abi3) didn't support it. Work toward a stable ABI usable by free-threaded builds is targeted at Python 3.15 (see PEP 803); if it lands as proposed, one extension wheel could serve both builds across versions. Check the 3.15 "What's New" before relying on it.

Subinterpreters: concurrent.interpreters

A third model sits between threads and processes. A subinterpreter is a separate Python interpreter inside the same process: its own modules, its own sys, its own objects, and, since 3.12 (PEP 684), its own GIL. Several subinterpreters running in different threads execute Python truly in parallel, even on a standard GIL build. Python 3.14 exposes this through the new concurrent.interpreters module (PEP 734) and concurrent.futures.InterpreterPoolExecutor.

Like processes

Isolated: no shared Python objects, so no data races on your objects. Communicate by passing data (queues, pickling).

Like threads

One OS process: faster to start than a process and lower memory; no fork hazards; cheap to exchange certain data such as bytes and memoryview buffers.

Caveats

New and evolving. Extension modules must support multiple interpreters (many do not yet). Startup still costs (each imports its own modules). Not available in the browser.

Only "shareable" objects cross between interpreters directly (interpreters.is_shareable(obj)): None, bool, int, float, str, bytes, tuples of shareable objects, memoryview, and interpreter queues. Other objects passed through call() or the executor are pickled, with the same constraints as multiprocessing.

Practice

Write speedup(p, n) returning the Amdahl speedup for parallel fraction p (0 to 1) on n workers, and workers_needed(p, target) returning the smallest integer n whose speedup is at least target, or None if the target is impossible (at or above the limit 1 / (1 - p)). Raise ValueError if p is outside [0, 1] or n < 1.

Hint

Solve 1 / ((1 - p) + p / n) >= target for n, or just loop upward from 1 (the loop terminates because you've already excluded impossible targets). Beware floating-point: compare with a tiny tolerance.

Show solution 
def speedup(p, n):
    if not 0 <= p <= 1 or n < 1:
        raise ValueError("need 0 <= p <= 1 and n >= 1")
    return 1 / ((1 - p) + p / n)

def workers_needed(p, target):
    if p < 1 and target >= 1 / (1 - p) - 1e-12:
        return None
    n = 1
    while speedup(p, n) < target - 1e-12:
        n += 1
    return n

Using generators as simulated threads, write run_round_robin(tasks) that advances each generator one step at a time in round-robin order (task 0, 1, 2, 0, 1, 2, ...) until all are exhausted, dropping finished ones. Then write simulate(n_tasks, increments, atomic) that resets a shared state = {"count": 0}, creates n_tasks generators that each increment state["count"] increments times, runs them round-robin, and returns the final count. When atomic is False, each increment must yield between reading and writing (a switch point inside the read-modify-write); when True, read and write happen with no yield in between (yield once after the write instead).

Hint

Keep a list of live generators; loop over a copy, call next(g) inside try, and remove it on StopIteration. Define the worker generator inside simulate so it closes over state.

Show solution 
def run_round_robin(tasks):
    live = list(tasks)
    while live:
        for task in list(live):
            try:
                next(task)
            except StopIteration:
                live.remove(task)

def simulate(n_tasks, increments, atomic):
    state = {"count": 0}

    def worker():
        for _ in range(increments):
            if atomic:
                state["count"] += 1
                yield
            else:
                value = state["count"]
                yield                      # switch point inside read-modify-write
                state["count"] = value + 1

    run_round_robin([worker() for _ in range(n_tasks)])
    return state["count"]

Parallel workers usually get contiguous slices of the input. Write chunk_ranges(n, workers) returning a list of (start, stop) pairs that cover range(n) exactly once, in order, with sizes differing by at most one (larger chunks first). Never return empty chunks: if workers > n, return n chunks of size 1. n == 0 returns []. Raise ValueError if workers < 1 or n < 0.

Hint

size, extra = divmod(n, k) with k = min(workers, n); the first extra chunks get size + 1 items.

Show solution 
def chunk_ranges(n, workers):
    if workers < 1 or n < 0:
        raise ValueError("need workers >= 1 and n >= 0")
    k = min(workers, n)
    if k == 0:
        return []
    size, extra = divmod(n, k)
    chunks, start = [], 0
    for i in range(k):
        stop = start + size + (1 if i < extra else 0)
        chunks.append((start, stop))
        start = stop
    return chunks

Write collect(futures) that takes a list of finished concurrent.futures.Future objects and returns (results, errors): results is a list of the successful results in input order, and errors is a list of (index, exception) pairs for futures that raised. Cancelled futures count as errors with a CancelledError instance. Never let an exception escape.

Hint

Check f.cancelled() first (calling exception() on a cancelled future raises). Otherwise f.exception() returns the exception or None.

Show solution 
from concurrent.futures import Future, CancelledError

def collect(futures):
    results, errors = [], []
    for i, f in enumerate(futures):
        if f.cancelled():
            errors.append((i, CancelledError()))
            continue
        exc = f.exception()
        if exc is None:
            results.append(f.result())
        else:
            errors.append((i, exc))
    return results, errors

Quiz

Recap

  • Concurrency is structure; parallelism is simultaneous execution. Identify I/O-bound vs CPU-bound work first, and bound your expectations with Amdahl's law.
  • The GIL protects interpreter internals, is released during blocking I/O and by many C extensions, and never made your code thread-safe.
  • Threads share memory: protect compound operations with Lock/RLock/Condition, or pass data through queue.Queue.
  • concurrent.futures gives one API over thread, process, and interpreter pools.
  • Processes are isolated and parallel but pay for pickling; 3.14 defaults to forkserver on Linux; use shared memory for big arrays.
  • Free-threaded 3.14 (python3.14t) is officially supported: true thread parallelism, ~5–10% single-thread cost, and your own thread-safety discipline.
  • concurrent.interpreters and InterpreterPoolExecutor give isolated parallelism inside one process.
