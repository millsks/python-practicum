ML in Production

A model in a notebook is a prototype. A model in production is software that other systems depend on: it must be reproducible, versioned, tested, served reliably, watched for decay, and fair to the people it affects. This module covers the engineering around the model, which is where most real ML work happens.

The ML lifecycle

Industry surveys and experience agree on an uncomfortable fact: the model-fitting code is a small fraction of a production ML system. Around it sit data collection, validation, feature pipelines, serving infrastructure, monitoring, and the processes to retrain safely. The work is a loop: once deployed, the world changes, monitoring notices, and you go around again.

Reproducibility

"It worked on my laptop last month" is not good enough when a regulator, a colleague, or you in six months asks why the model made a decision. A training run is reproducible when the same code, data, environment, and configuration give the same model. Control all four:

  • Randomness: pass explicit seeds everywhere: np.random.default_rng(seed), random_state=seed in scikit-learn, torch.manual_seed(seed). Avoid global random state. (Some GPU operations are nondeterministic even with seeds; frameworks document flags for deterministic mode.)
  • Environment: pixi.lock pins the exact version and build of every package, Python included, for every platform. Commit it. pixi install --locked fails rather than silently changing versions, which is what you want in CI and in production images.
  • Code: the git commit hash of the training code.
  • Data: data changes under you. Record a fingerprint (a hash of the file or of a canonical serialization) and keep immutable, dated snapshots. Tools such as DVC or lakeFS version large datasets alongside git; a content hash in your run metadata is the minimum.

A reproducible training project typically has [tasks] train = "python -m churn.train --config configs/v3.toml" in pixi.toml, a committed pixi.lock, and a CI job that runs pixi run --locked train on a small sample. Anyone can then reproduce a run with one command.

You will train dozens of variants. An experiment tracker records each run's parameters, metrics, artifacts (plots, the model file), code version, and data fingerprint, and lets you compare runs in a UI. Evaluation beyond accuracy

Calibration

When a model says "70% chance of default", do 70% of such customers actually default? If so, the model is calibrated. Calibration matters whenever probabilities feed a decision (pricing, triage, expected revenue). A reliability diagram bins predictions by predicted probability and plots the observed frequency in each bin: a calibrated model follows the diagonal. Two summary numbers: the Brier score (mean squared error of probabilities; lower is better) and the expected calibration error (the average gap between confidence and frequency, weighted by bin size). Logistic regression tends to be well calibrated; tree ensembles and naive Bayes often are not. CalibratedClassifierCV fixes a model's probabilities with sigmoid (Platt) or isotonic regression fitted on held-out folds.

Slicing by subgroup

An overall metric can hide a model that works well for most people and badly for some. Slice your evaluation by meaningful groups (region, device, age band, new vs returning customers) and compare. Large gaps are bugs to investigate: often a group is underrepresented in training data, or a feature means something different for it.

Fairness checks

When predictions affect people (loans, hiring, healthcare), check whether outcomes differ across protected groups. Two common, simple metrics compare groups A and B:

  • Demographic parity difference: difference in the rate of positive predictions (P(ŷ = 1 | A) − P(ŷ = 1 | B)).
  • Equal opportunity difference: difference in recall (true-positive rate) between groups: qualified people should be approved at the same rate regardless of group.

These criteria can conflict with each other and with accuracy, and no metric settles what is fair; that is a decision for people, informed by law and context. Removing the protected attribute from the features does not guarantee fairness, because other features (postcode, for example) can act as proxies. Libraries such as Fairlearn provide these metrics and mitigation methods.

Remember: check calibration when probabilities matter, slice metrics by subgroup, and measure fairness gaps explicitly; decide trade-offs with stakeholders.

Model persistence and versioning

M56 showed how to save a fitted pipeline with joblib or skops. In production you also need to know, for any deployed model: what it is, how it was made, and whether it is safe to load. Save a bundle: the model file plus a metadata file with the model version, training date, data fingerprint, code commit, library versions, input schema, evaluation metrics, and decision threshold. Give models version numbers (for example churn-model 3.2.0, where a major bump means the input schema changed).

A model registry (MLflow's, or a cloud provider's) stores these bundles and tracks their stage: "staging", "production", "archived". Promotion to production should be a reviewed, reversible step, and rollback to the previous version should be one command.

Remember: a model is a file plus metadata; version it, register it, and make rollback easy.

Serving a model: batch vs online

Batch prediction

A scheduled job scores many rows at once (every night, score all customers for churn risk) and writes results to a table that other systems read. Simple, cheap, easy to retry and audit. Predictions can be hours old.

Online prediction

A service answers one request at a time, in milliseconds (score this transaction for fraud now). Needs low latency, high availability, input validation, and features that are available at request time.

Prefer batch unless the decision truly needs fresh, per-request predictions. For online serving, a small web API is the usual shape. Using FastAPI from M45, the model loads once at startup, a Pydantic model validates every request against the input schema, and each prediction is logged as a structured event with structlog (not print) so it can be monitored later.

Invalid input (a negative tenure, a missing field) is rejected by Pydantic with a 422 response before it reaches the model. The same validation idea, written by hand, is a good exercise and appears in this module's practice.

Training/serving skew is a classic production bug: the features at serving time are computed differently from training (a different unit, a missing default, a newer category list). Shipping the whole fitted Pipeline, preprocessing included, and validating inputs against the training schema prevents most of it.

Remember: batch when you can, online when you must; load once, validate every input, log every prediction as a structured event.

Monitoring, data drift, and concept drift

Deployed models decay because the world changes. Two kinds of change:

  • Data drift (covariate shift): the distribution of inputs changes. A marketing campaign brings younger customers; a sensor is recalibrated. The model may now be extrapolating.
  • Concept drift: the relationship between inputs and the target changes. Fraudsters adopt a new trick; a pandemic changes what "normal" spending looks like. The same inputs now mean different outcomes.

Concept drift shows up only when true outcomes (labels) arrive, which can take weeks. Data drift can be detected immediately by comparing recent inputs with a reference window (usually the training data). So production monitoring tracks: input distributions per feature, the prediction distribution, missing-value and error rates, latency, and, once labels arrive, the real metric.

Two drift tests

  • The two-sample Kolmogorov-Smirnov (KS) test (scipy.stats.ks_2samp) compares two samples of a numeric feature. Its statistic is the largest vertical gap between the two empirical cumulative distribution functions; a small p-value says "these probably come from different distributions". With very large samples, even trivial differences become "significant", so also look at the statistic's size.
  • The population stability index (PSI) bins the reference into (say) 10 quantile bins and compares the fraction of reference and current data in each: PSI = Σ (cur − ref) · ln(cur / ref). A common rule of thumb: below 0.1 stable, 0.1–0.25 moderate shift, above 0.25 significant shift. Popular in credit scoring because it is simple to compute and explain.

Alert on drift, but do not retrain blindly. Investigate first: a drift alert may be a broken upstream pipeline (a column suddenly all zeros) rather than a changing world. Automated retraining needs the same evaluation gates as the first release, plus a comparison against the current production model.

Remember: data drift = inputs change (detect now with KS/PSI); concept drift = the input-target relationship changes (detect when labels arrive); monitor inputs, outputs, and outcomes.

Testing ML code

ML systems need ordinary software tests (M17) plus tests specific to data and models. Run them with pixi run pytest in CI like any other project.

# tests/integration/test_behavior.py
import pytest
from churn.model import load_bundle

@pytest.mark.integration
def test_more_support_calls_never_lowers_risk(sample_customer):
    model = load_bundle("bundle/")
    low = model.predict_proba(sample_customer(support_calls=0))[0, 1]
    high = model.predict_proba(sample_customer(support_calls=8))[0, 1]
    assert high >= low, "directional expectation agreed with the business"

@pytest.mark.integration
def test_minimum_quality(holdout):
    model = load_bundle("bundle/")
    assert holdout.roc_auc(model) >= 0.80, "release gate: never ship below the agreed floor"
  • Unit tests for features: pure functions with small hand-made DataFrames, including edge cases (zero, missing, unseen categories).
  • Data validation tests: schema, ranges, null rates, uniqueness of keys, run on every new batch (libraries like pandera or Great Expectations help).
  • Golden datasets: a small committed input file with reviewed expected outputs; catches accidental changes to preprocessing or model loading.
  • Behavioral tests: invariance (changing a name should not change a credit score), directional expectations, and minimum-performance gates on a frozen holdout.
  • Training smoke test: train on 200 rows in CI to prove the pipeline runs end to end.

Remember: test features like functions, data like inputs, and models like behavior; gate releases on a frozen holdout.

Responsible AI

Models make or shape decisions about people. Responsible practice is part of the engineering, not an afterthought:

Purpose and harm

Write down who is affected, how a wrong prediction hurts them, and whether ML is appropriate at all. Some decisions need a human.

Data and privacy

Collect only what you need, with consent and a legal basis; protect personal data; know where training data came from and whether you may use it.

Fairness

Measure performance and outcome rates across groups (this module's slices), investigate gaps, and document the trade-offs you chose.

Transparency

Publish a model card: intended use, training data, metrics overall and by slice, limitations, and contacts. Explain individual decisions where people are affected.

Human oversight

Provide a way to appeal or override, route low-confidence cases to people, and keep an audit log of predictions.

Security

Validate inputs, never load untrusted model files (M56), and consider abuse: adversarial inputs, data poisoning, model extraction.

A hospital wants a model to prioritize patients for follow-up calls. Its training label is "past healthcare spending" as a stand-in for "health need". Which group could this systematically disadvantage, and why? (Groups who historically had less access to care spend less at the same level of need, so a model trained on spending under-prioritizes them. The choice of label is itself a fairness decision.)

Remember: define harm, protect data, measure fairness, document with model cards, keep humans in the loop.

Practice

NumPy, SciPy, and pandas are available.

Write psi(reference, current, bins=10). Use quantiles of reference as bin edges (np.quantile(reference, np.linspace(0, 1, bins + 1))), replace the first and last edges with -inf and inf, compute the fraction of each sample per bin, clip fractions to at least 1e-6, and return Σ (cur − ref) · ln(cur / ref) as a float.

Hint

np.histogram(x, edges)[0] / len(x) gives the fractions; np.clip(frac, 1e-6, None) avoids log(0).

Show solution 
import numpy as np

def psi(reference, current, bins=10):
    edges = np.quantile(reference, np.linspace(0, 1, bins + 1))
    edges[0], edges[-1] = -np.inf, np.inf
    ref = np.clip(np.histogram(reference, edges)[0] / len(reference), 1e-6, None)
    cur = np.clip(np.histogram(current, edges)[0] / len(current), 1e-6, None)
    return float(np.sum((cur - ref) * np.log(cur / ref)))

Write validate(record, schema) that returns a list of error strings (empty when valid). The schema maps each field name to a dict with "type" (int, float, or str) and optionally "min", "max" (numbers) or "allowed" (a set of strings). Rules: every schema field is required ("missing: name"); unknown fields are errors ("unexpected: name"); a wrong type gives "type: name" (an int is acceptable for a float field, but bool is never a number); out-of-range gives "range: name"; a string not in allowed gives "value: name". Report fields in schema order, then unexpected fields in sorted order.

Hint

Check type first and continue on a type error so you do not compare a string with a number. For floats accept (int, float); reject bool explicitly because isinstance(True, int) is True.

Show solution 
def validate(record, schema):
    errors = []
    for name, rule in schema.items():
        if name not in record:
            errors.append(f"missing: {name}")
            continue
        value = record[name]
        expected = rule["type"]
        accepted = (int, float) if expected is float else (expected,)
        if isinstance(value, bool) or not isinstance(value, accepted):
            errors.append(f"type: {name}")
            continue
        if "min" in rule and value < rule["min"] or "max" in rule and value > rule["max"]:
            errors.append(f"range: {name}")
        if "allowed" in rule and value not in rule["allowed"]:
            errors.append(f"value: {name}")
    errors.extend(f"unexpected: {name}" for name in sorted(set(record) - set(schema)))
    return errors

Write metrics_by_group(y_true, y_pred, groups) returning a dict mapping each group value to a dict with "n" (int), "accuracy", "recall" (true-positive rate; 0.0 if the group has no positives), and "positive_rate" (fraction predicted 1), all floats. Then write max_gap(by_group, metric) returning the largest minus the smallest value of that metric across groups.

Hint

Convert to arrays, loop over np.unique(groups), and build a boolean mask per group.

Show solution 
import numpy as np

def metrics_by_group(y_true, y_pred, groups):
    t, p, g = np.asarray(y_true), np.asarray(y_pred), np.asarray(groups)
    result = {}
    for value in np.unique(g):
        m = g == value
        positives = t[m] == 1
        result[value.item()] = {
            "n": int(m.sum()),
            "accuracy": float(np.mean(t[m] == p[m])),
            "recall": float(np.mean(p[m][positives] == 1)) if positives.any() else 0.0,
            "positive_rate": float(np.mean(p[m] == 1)),
        }
    return result

def max_gap(by_group, metric):
    values = [stats[metric] for stats in by_group.values()]
    return max(values) - min(values)

Write drift_report(reference, current, alpha=0.01) where both arguments are dicts mapping feature names to 1-D arrays. For every feature in reference, run scipy.stats.ks_2samp and return a dict mapping the name to {"statistic": float, "p_value": float, "drifted": bool} where drifted is p_value < alpha.

Hint

result = ks_2samp(a, b) has .statistic and .pvalue; wrap them in float() and the comparison in bool().

Show solution 
from scipy.stats import ks_2samp

def drift_report(reference, current, alpha=0.01):
    report = {}
    for name, ref_values in reference.items():
        result = ks_2samp(ref_values, current[name])
        p_value = float(result.pvalue)
        report[name] = {"statistic": float(result.statistic), "p_value": p_value, "drifted": bool(p_value < alpha)}
    return report

Write ece(y_true, proba, n_bins=10). Split [0, 1] into n_bins equal-width bins (a probability of exactly 1.0 goes in the last bin). For each non-empty bin, take |mean(proba in bin) − mean(y_true in bin)| and weight it by the fraction of samples in the bin. Return the sum as a float.

Hint

idx = np.minimum((proba * n_bins).astype(int), n_bins - 1) gives each sample's bin.

Show solution 
import numpy as np

def ece(y_true, proba, n_bins=10):
    y, p = np.asarray(y_true, dtype=float), np.asarray(proba, dtype=float)
    idx = np.minimum((p * n_bins).astype(int), n_bins - 1)
    total = 0.0
    for b in range(n_bins):
        m = idx == b
        if m.any():
            total += m.mean() * abs(p[m].mean() - y[m].mean())
    return float(total)

Mini-project

Mini-projectPackage a model for production

Turn the churn model from M56 (or any classifier you trained) into a small, tested, installable package that another team could use safely. Create it with pixi init churn-service, a src/churn/ layout, and pixi add scikit-learn pandas scipy structlog pytest.

  1. churn/train.py: trains the pipeline with fixed seeds and writes a bundle directory: model.joblib, metadata.json (version, data fingerprint, library versions, metrics, threshold, feature schema), and reference.parquet or .csv (a sample of training inputs for drift checks). Expose it as pixi run train.
  2. churn/schema.py: the feature schema and a validate(record) function (like the exercise) that raises a custom SchemaError listing every problem.
  3. churn/predict.py: load(bundle_dir) verifies the model file's SHA-256 against the metadata before loading, and predict(records: list[dict]) -> list[dict] validates every record and returns probability, decision, and model version. Log each call with structlog (key=value or JSON output).
  4. churn/drift.py: check_drift(current_df) returns per-feature KS statistics and PSI against the bundle's reference sample, flagging features above your thresholds.
  5. Tests: unit tests for the schema and drift functions; a golden test with five fixed customers; a test that a tampered model file is refused; and a behavioral test (more support calls never lowers churn risk).
  • pixi run train twice produces identical metrics and the same data fingerprint
  • predict() rejects invalid records with a clear, complete error message
  • Loading refuses a model whose hash does not match the metadata
  • check_drift() flags an artificially shifted feature and passes an unshifted sample
  • Logs are structured events, not print output
  • pixi run pytest passes, including golden and behavioral tests
  • A short MODEL_CARD.md documents intended use, metrics by slice, and limitations

Stretch: wrap predict() in the FastAPI app from this module (pixi add fastapi uvicorn); add a calibration check to the release gate; track training runs in MLflow.

  • Production ML is a loop: frame → data → train → evaluate → package → deploy → monitor → back again.
