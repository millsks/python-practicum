Project 6: Habit Tracker Service

Build a professional-grade habit tracker the way teams build real services: a pure domain at the center, Protocol ports around it, swappable in-memory and SQLite adapters, a service layer of use cases, and a structlog-instrumented CLI on the outside. Ninety-seven tests tell you when each layer is right.

⏱ ~8–12 hoursPrerequisites: M44, M45, M46, M42
  • Model a domain with frozen dataclasses and pure functions that are trivial to test
  • Define ports as typing.Protocols and write two adapters that satisfy the same contract
  • Use sqlite3 professionally: versioned migrations, transactions, and parameterized queries
  • Write use cases that depend on a Clock abstraction instead of the real date
  • Build an argparse CLI that separates results (stdout) from structured logs (stderr)
  • Run one contract test suite against several implementations with a parametrized fixture

The scenario

A small product team wants a habit tracker. Users create habits ("Drink water", "Gym on Mon/Wed/Fri", "Weekly review"), check in when they do them, and look at their streaks (how many periods in a row they kept the habit) and completion rate (what fraction of due periods they kept). Today it is a command-line tool backed by a SQLite file. Next quarter the team wants a web API (Module 45's FastAPI) and maybe PostgreSQL. Your job is to build version 1 so that those changes touch only the edges of the code.

That requirement drives the architecture. The rules about dates and streaks are the valuable, subtle part, so they live in a domain module with no I/O at all. Storage is hidden behind a port (an interface), so a SQLite adapter and an in-memory adapter are interchangeable. The service layer expresses each use case once. The CLI is a thin composition root: the one place that picks concrete classes and wires them together.

Before reading further: if "today" were read with date.today() deep inside the streak code, how would you write a test for "the streak survives until midnight"? Keep your answer in mind when you meet the Clock port.

Feature specification

Frequencies and periods

Every habit has a frequency, and every frequency splits time into periods. A period is identified by its key, the date it starts on.

Dailydailyone day (key = the day)every day
Weeklyweeklyone ISO week (key = its Monday)every day of the week
Specific weekdaysmon,wed,frione dayonly the listed days

Rules

  • Habit ids are slugs of the name: "Drink Water!" becomes drink-water. Names are 1–80 characters after stripping; duplicate ids are rejected.
  • Check-in is idempotent per period. Checking in a weekly habit on Monday and again on Thursday stores one completion; the second call returns False.
  • Check-ins in the future, before the habit was created, on a day that is not due, or on an archived habit raise ValidationError. Unknown ids raise NotFoundError.
  • Undo removes the check-in for the period that contains the given day (default today).
  • Current streak: consecutive satisfied periods ending at the current one. Today's period is still in progress, so leaving it unchecked does not break the streak; a missed finished period does.
  • Longest streak: the best run of consecutive satisfied periods from creation until today.
  • Completion rate over start..end: satisfied due periods divided by due periods, ignoring periods before creation (0.0 if there are none). The default window is the 30 days ending today.
  • Export: JSON (every habit with its list of check-in dates and streaks) and CSV (one row per habit with the check-in count).

The CLI

pixi run python -m habits --db demo.db export --format json > backup.json
pixi run python -m habits -v --today 2026-02-01 undo gym       # -v shows info logs on stderr

Global options: --db PATH (default $HABITS_DB, else habits.db), --today YYYY-MM-DD (pretend it is that date; great for demos and tests), and -v. Exit code 0 means success, 1 means a HabitError (message on stderr as error: ...), and 2 is argparse's usage error.

Results go to stdout through sys.stdout.write in cli.py only, so export > backup.json produces a clean file. Diagnostics are structlog events rendered as key=value on stderr, for example timestamp='2026-01-05T09:00:00Z' level='info' event='checked_in' day='2026-01-05' habit_id='gym'. No library module calls print(). This is the Unix convention: data on stdout, chatter on stderr.

Architecture

Dependencies point inward. The domain imports nothing from the project. Ports import only the domain. The service imports the domain and the ports, never an adapter. Only the CLI knows that SQLite exists.

Hints

Hint: the streak walk

Think in period keys, not dates. Build the set of satisfied keys once ({freq.period_start(c.day) for c in completions if ...}). Then start at the last due period on or before today and step backwards with previous_period while the key is in the set. The only special case: if that starting key is today's period and it is not satisfied yet, step back once before counting.

key = last_due_period(habit, today)
if key not in done and key == freq.period_start(today):
    key = freq.previous_period(key)       # today is still in progress
streak = 0
while key >= first and key in done:
    streak += 1
    key = freq.previous_period(key)
Hint: atomic migrations in sqlite3

Python's sqlite3 module implicitly opens a transaction only before INSERT/UPDATE/ DELETE, not before CREATE TABLE. To make "run these DDL statements and bump the version" all-or-nothing, issue BEGIN yourself inside with conn:; the context manager commits on success and rolls back on an exception.

for version in range(current, LATEST_VERSION):
    with conn:
        conn.execute("BEGIN")
        for statement in MIGRATIONS[version]:
            conn.execute(statement)
        conn.execute("UPDATE schema_version SET version = ?", (version + 1,))
Hint: detecting duplicates without a race

Don't SELECT first and then INSERT: another process could insert in between. Let the database enforce the rule. For habits, catch sqlite3.IntegrityError from the primary key and re-raise DuplicateHabitError(...) from exc. For completions, INSERT OR IGNORE and check cursor.rowcount.

Hint: structlog and swapped streams in tests

structlog.PrintLoggerFactory(file=sys.stderr) captures the stream object at configuration time. pytest's capsys replaces sys.stderr per test and closes the old one, so later log calls would fail with "I/O operation on closed file". The given configure_logging uses a small factory that looks up sys.stderr at each call and turns off cache_logger_on_first_use.

Hint: one contract, two adapters 
@pytest.fixture(params=["memory", "sqlite"])
def repo(request, tmp_path):
    if request.param == "memory":
        yield InMemoryRepository()
    else:
        with SqliteRepository(tmp_path / "habits.db") as sqlite_repo:
            yield sqlite_repo

If a contract test passes for memory but fails for SQLite, the difference is usually ordering (add ORDER BY), type conversion (dates stored as ISO text, booleans as 0/1), or a missing NotFoundError when UPDATE affects zero rows (check cursor.rowcount).
