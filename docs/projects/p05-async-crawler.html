Project 5: Async Web Crawler

Build a polite, resilient, concurrent crawler that walks a documentation site and reports every broken link along with the pages that point to it. It is the kind of tool teams run in CI every night, and it exercises every hard part of asyncio: bounded concurrency, rate limiting, retries, structured shutdown, and cancellation.

⏱ ~8–10 hoursPrerequisites: M38, M40 (also uses M37 and M16)
  • Design around an injected async Protocol so network code is testable offline
  • Run a bounded worker pool fed by an asyncio.Queue inside a TaskGroup
  • Implement per-host rate limiting and retries with exponential backoff and jitter
  • Shut down cleanly with sentinels and stay correct under cancellation
  • Parse HTML and URLs with the standard library (html.parser, urllib.parse, urllib.robotparser)
  • Produce a deterministic JSON report suitable for CI

The scenario

Your team's documentation site has grown to hundreds of pages written by dozens of people. Pages get renamed, sections move, and readers keep landing on 404s. You are asked for a tool that can run in CI and answer one question: which links are broken, and where are they? A plain "this URL is a 404" is not enough. The writer fixing it needs the referrers, the pages that contain the bad link.

Fetching pages one at a time is far too slow: a 300-page site at 200 ms per request takes a minute, and most of that time the program sits idle waiting on the network. That is exactly the I/O-bound workload asyncio was built for (M38). But unbounded concurrency would hammer the server, so the crawler must also be polite: obey robots.txt, cap concurrent requests, and space out requests per host.

Only crawl sites you own or have permission to crawl, and keep the per-host interval generous (one second or more) when you run the real fetcher. The graded tests never touch the network.

Learning goals

Dependency injection

The crawler depends on a Fetcher Protocol, not on urllib. Tests inject FakeFetcher; production injects UrllibFetcher.

Structured concurrency

Workers live inside a TaskGroup: none can leak, and a crash in one cancels the rest and surfaces as an ExceptionGroup.

Back-pressure and politeness

A fixed worker pool bounds concurrency; a per-host limiter bounds request rate; Crawl-delay from robots.txt can raise it.

Resilience

Transient failures (connection resets, 429, 503) are retried with capped exponential backoff and full jitter, using an injected sleep and Random.

Architecture

The crawl is a classic producer/consumer pipeline where the consumers are also producers: each worker pulls a Job(url, depth, referrer), fetches it, and pushes newly discovered links back onto the same queue. The queue's unfinished-task counter is what tells us we are done: queue.join() returns only when every job that was ever put has had a matching task_done().

  REP --> J[CrawlReport.to_json]

Why can't we simply wait until the queue is empty? Because a worker may be in the middle of fetching a page that will add ten more links. "Empty" is a momentary state; "every put has a matching task_done" is the real termination condition.

Milestones

Milestone 1: URLs and links

Implement remove_dot_segments, normalize_url, host_of, same_site, robots_url, and extract_links. Normalization is what makes de-duplication work: HTTP://Docs.Example.com:80/a/./b/../c#top and /a/c on that site are the same page.

  • Relative links resolve against the page (and <base href>)
  • mailto:, javascript:, fragments-only, and bad ports return None
  • same_site resists the example.com.evil.org suffix trick
  • pixi run practicum grade p05 -k "urls or links" passes

Milestone 2: robots.txt

Wrap urllib.robotparser.RobotFileParser in RobotsPolicy. A 404 robots.txt means "no rules". Note that RobotFileParser only accepts whole-second Crawl-delay values.

  • allowed() honors per-agent rules
  • crawl_delay() returns 0.0 when unset
  • -k robots passes

Milestone 3: politeness and resilience

Build HostRateLimiter and fetch_with_retries. Both take an injected sleep (and the limiter a clock), so tests advance virtual time instantly instead of waiting.

  • Concurrent callers for one host are serialized one interval apart
  • Different hosts never wait for each other
  • Backoff ceilings double and cap; delays are jittered in [0, ceiling]
  • 404 is final; 503 and FetchError are retried
  • -k "retry or ratelimit" passes

Milestone 4: the engine

Implement Crawler.crawl, the worker loop, scheduling, robots caching, and page processing.

  • Each URL is fetched exactly once even when linked from many pages
  • Referrers are recorded for every link, including duplicates
  • max_depth, max_pages, redirects, external links, and blocked URLs behave as specified
  • Peak in-flight requests equals concurrency

Milestone 5: shutdown and cancellation

Make the crawl end cleanly and fail loudly. Every queue.get() is paired with task_done() in a finally; in_progress is cleaned in a finally; the TaskGroup guarantees no worker outlives crawl().

  • asyncio.timeout around crawl() leaves zero leftover tasks
  • A partial report() is available after cancellation
  • A non-transient bug in the fetcher surfaces as an ExceptionGroup
  • A Crawler can be reused for a second crawl

Milestone 6: report and CLI

Implement build_report, CrawlReport.to_dict/to_json, and cli.main. Sort everything so the JSON is deterministic: CI diffs should show real changes only.

  • Report summary matches the documented shape
  • CLI exits 0, 1, or 2 as specified
  • pixi run grade p05: all 81 tests pass

The heart of it: worker pool and shutdown

This is the shape the tests expect. Study why each try/finally is there before you write yours.

async def crawl(self, start_url: str) -> CrawlReport:
    start = normalize_url(start_url)
    if start is None:
        raise ValueError(f"not a crawlable URL: {start_url!r}")
    self._reset(start)
    queue: asyncio.Queue[Job | None] = asyncio.Queue()
    self._schedule(queue, Job(start, 0, None))
    async with asyncio.TaskGroup() as group:
        for i in range(self.config.concurrency):
            group.create_task(self._worker(queue), name=f"crawler-worker-{i}")
        await queue.join()                  # every put has a matching task_done
        for _ in range(self.config.concurrency):
            queue.put_nowait(None)          # one sentinel per worker
    return self.report()

async def _worker(self, queue):
    while True:
        job = await queue.get()
        try:
            if job is None:
                return
            ...                             # robots, rate limit, fetch, parse, schedule
        finally:
            queue.task_done()               # even on error or cancellation

The alternative shutdown, cancelling workers after join(), also works inside a TaskGroup (cancelled children do not count as errors). Sentinels are preferred here because a worker is never interrupted mid-fetch during a normal shutdown.

Hints

My crawl hangs forever

Almost always a missing queue.task_done(). If a worker returns early (blocked by robots, a redirect, an exception) without calling it, queue.join() never returns. Put task_done() in a finally right after get().

robots.txt is fetched several times

Several workers reached the same host at once and all saw an empty cache. Guard the check-and-fetch with a per-host asyncio.Lock: the second worker waits, then finds the cached policy. This is a race even though asyncio is single-threaded, because there is an await between the check and the store.

The rate-limit test sees requests at the same instant

Record the "last request" time after sleeping and while still holding the host's lock. If you compute the wait outside the lock, two callers compute the same wait and wake up together.

The cancellation test finds leftover tasks

Create workers with group.create_task, not asyncio.create_task. Only tasks owned by the TaskGroup are cancelled and awaited when the body is cancelled.

A redirect target is fetched twice

Send the normalized Location through the same _schedule path as ordinary links, so the seen set de-duplicates it.

Why asyncio.to_thread for urllib?

urllib blocks. Calling it directly inside a coroutine would freeze the event loop, and with it every other worker. to_thread runs it in the default thread pool; the loop keeps scheduling other coroutines while the thread waits on the socket (and the GIL is released during socket I/O).
