Project 7: City Data EDA Report

Turn a messy export of a city's 311 service requests into a cleaned dataset, honest statistics, clear charts, and a Markdown report a city manager can read. Every cleaning decision is documented and every number is reproducible, because the tests check the exact values.

⏱ ~8–12 hoursPrerequisites: M51, M53, M54 (and M50 for scipy.stats)
  • Load raw data with explicit dtypes instead of letting pandas guess
  • Design cleaning rules as small, ordered, logged steps whose effects can be counted and tested
  • Engineer features from timestamps and detect outliers relative to each group
  • Quantify uncertainty with a bootstrap confidence interval and compare groups with a nonparametric test
  • Produce publication-quality charts headlessly with matplotlib's Figure API
  • Assemble a reproducible pipeline that writes a Markdown report, verified by 60+ tests

The scenario

Every large city runs a 311 line: the non-emergency number (and app) where residents report noise, missing heat, potholes, broken street lights, and illegal parking. Each report becomes a service request with an ID, a creation time, a closing time once resolved, a category, and a borough.

The deputy mayor's office wants a monthly exploratory data analysis (EDA) report: what people complain about, where, how the volume is trending, how long the city takes to resolve requests, and whether one borough is being served more slowly than another. Last month an analyst built it by hand in a spreadsheet; nobody can reproduce the numbers, and the borough totals did not add up because BROOKLYN, Bklyn, and Brooklyn were counted separately.

Your job is to build cityeda, a small Python package that runs the whole analysis from the raw export to report.md plus charts, with a cleaning log that explains every row that was dropped or changed. The raw export is genuinely messy:

  • borough names in many spellings (BRONX, The Bronx, BX), and some blank;
  • categories with random casing and stray spaces ( STREET LIGHT );
  • creation dates that are not dates at all (not a date, 31/02/2025, N/A);
  • closing dates of unknown, and some requests that "close" before they were opened;
  • a few requests that took thousands of hours, and request IDs that appear twice.

Because the real export cannot be shipped with the course, the package includes a deterministic synthetic generator, generate_requests(n, seed), that produces a realistic CSV with exactly known amounts of each kind of mess. That is what lets the tests check your cleaning counts and statistics exactly.

Learning goals and feature spec

0. cityeda.generate (provided)

generate_requests(n=2000, seed=311) -> str returns CSV text with n + n // 50 rows; write_requests(path, n, seed) writes it. mess_counts(n) tells you exactly how many rows of each kind of mess were injected. You do not change this module.

1. cityeda.load

RAW_DTYPES maps every column to an explicit dtype: text as "str" (dates stay text for now), channel and status as "category". load_requests(path) raises ValueError("... missing columns ...") if a column is absent and returns the columns in COLUMNS order.

2. cityeda.clean

normalize_borough, normalize_category, and clean_requests(raw) -> (frame, log) applying seven rules in order, each recorded as a CleaningStep(rule, description, rows_affected). The input is never modified.

3. cityeda.features

iqr_outliers(values, k=3.0) (Tukey fences) and add_features(df) adding resolution_hours, ordered weekday, hour, week (the Monday), and is_outlier computed within each category.

4. cityeda.analysis

requests_by (counts, largest first, ties alphabetical), resolution_summary (named aggregations), bootstrap_median_ci (seeded), weekly_trend (weekly counts and a rolling mean), and compare_boroughs (Mann-Whitney U).

5. cityeda.charts, report, pipeline

Three PNG charts via matplotlib.figure.Figure; markdown_table, render_report, write_report; run_pipeline(csv, out_dir) and a main() CLI that logs with structlog.

The seven cleaning rules

#Rule name (in the log)What it doesrows_affected counts
1drop_duplicate_idskeep the first row for each request_idrows removed
2normalize_categorycollapse whitespace and title-caserows whose value changed
3normalize_boroughmap spellings to Manhattan, Brooklyn, Queens, Bronx, Staten Islandnon-blank rows whose value changed
4fill_missing_boroughblank boroughs become "Unknown"blank rows
5drop_invalid_createddrop rows whose created_at does not parse with the exact formatrows removed
6null_invalid_closedunparseable closed_at becomes missing (NaT)values nulled
7null_closed_before_createdclosed_at earlier than created_at becomes missingvalues nulled

Why null an impossible closing time instead of dropping the row? The request still happened: it belongs in the volume counts. Only its duration is unknown. Dropping it would undercount requests; keeping the negative duration would corrupt the median. Each rule in the table makes that kind of trade-off explicitly, and the log makes it visible to the reader.

Milestone 2: Clean, and log every rule

Implement the normalizers first; they are plain functions on one value, easy to test in isolation. Then build clean_requests as a sequence of steps, appending a CleaningStep after each. Use df.assign(...), boolean masks, and Series.mask(...); under pandas 3.0 Copy-on-Write, chained assignment like df["closed_at"][mask] = pd.NaT silently does nothing. Parse dates with an explicit format= and errors="coerce", then count the NaTs you created.

  • normalize_borough handles casing, extra spaces, aliases, "The ...", blanks, and NaN
  • The log lists all seven rules in order with honest counts
  • Counts match mess_counts(n): duplicates, blanks, bad created, bad closed, closed-before-created
  • The cleaned frame is sorted by created_at with a fresh index and the input is unchanged
  • pixi run grade p07 -- -k cityeda_clean passes (24 tests including parametrized cases)

Milestone 3: Feature engineering

Subtracting two datetime columns gives a timedelta column; .dt.total_seconds() / 3600 turns it into hours (missing closing times stay NaN). weekday should be an ordered categorical so charts and group-bys list Monday to Sunday, not alphabetically. For outliers, a single global fence would flag every legitimately slow street-light repair, so compute the fences per category with groupby(...).transform(iqr_outliers).

  • resolution_hours is non-negative or NaN
  • weekday is ordered Monday..Sunday; hour is 0-23; week is a Monday
  • Every injected extreme (over 1,500 hours) is flagged, and fewer than 5% of rows are
  • pixi run grade p07 -- -k cityeda_features passes (7 tests)

Milestone 4: Analysis with uncertainty

Counts first: requests_by(df, "category") must order ties alphabetically so reports are stable. Then the statistics from M54: a percentile bootstrap for the median resolution time (resolution times are skewed, so the median is the honest "typical" value and there is no simple formula for its CI), a weekly trend with resample("W-MON", label="left", closed="left") and a 4-week rolling mean, and a Mann-Whitney U test comparing two boroughs. Why not a t-test? The data are heavily right-skewed with extreme values; a rank-based test is robust to that.

  • On the seed-311 dataset: 1,980 cleaned rows, Noise is top with 503, Bronx 366 vs Manhattan 362 requests
  • Median resolution is about 25.2 hours from 1,806 closed requests, with a deterministic bootstrap CI
  • The weekly trend has 26 weeks starting 2025-01-06 and sums to the row count
  • The borough comparison matches scipy.stats.mannwhitneyu and finds the Bronx slower
  • pixi run grade p07 -- -k cityeda_analysis passes (13 tests)

Hints

My duplicate count is right but the borough counts are off by one

Duplicates are exact copies, so a blank-borough row can be duplicated. Remove duplicates first (rule 1), then count blanks; the log counts are defined on the frame as it is at each step.

How do I count rows a normalizer "changed"?

Compute the new Series, compare with the old one (new != old), and sum the mask. For boroughs, exclude blank rows from that count (& ~missing) because they belong to rule 4.

pd.to_datetime accepts "2025-13-40 25:00:00" or warns about formats

Always pass format=TIMESTAMP_FORMAT and errors="coerce". With an explicit format, pandas rejects impossible dates instead of guessing, and does not emit format-inference warnings.

My closed_before_created rule changes nothing

That is the Copy-on-Write trap: df["closed_at"][backwards] = pd.NaT modifies a temporary copy. Write df = df.assign(closed_at=df["closed_at"].mask(backwards)), or use df.loc[backwards, "closed_at"] = pd.NaT on a frame you own.

My weekly trend has 27 rows or starts on a Sunday

The default weekly rule "W" means weeks ending Sunday, labelled by the Sunday. Use resample("W-MON", label="left", closed="left") so each bin starts on a Monday and is labelled by it.

My bootstrap interval changes every run

Create the generator inside the function from the seed argument (np.random.default_rng(seed)) and draw all resamples at once with rng.choice(data, size=(n_boot, data.size), replace=True), so the sequence of draws is fixed.

Tests about chart files fail with "no such file or directory"

Create the parent folder before saving: path.parent.mkdir(parents=True, exist_ok=True).
